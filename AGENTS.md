# Naming: Bot computer

People read "Bot computer" (owner, 10-31) for the computer a Bot uses; it is the umbrella term and can have kinds (backends). Two kinds: the built-in VM (Firecracker microVM on the TOFI host; label `computer:kind.vm`, "Built-in VM") and the E2B cloud computer that the person adds with their own E2B key (`internal/computer/e2b`; see "Environments and the E2B computer" below). The personal-computer pairing (Mac app, `TOFI_PERSONAL_COMPUTERS`, listed in Settings > Environments) is another thing and keeps its names. Code identifiers, tool names, JSON keys, API paths, env vars and CLI commands keep "computer". Model-facing text (`internal/app`, `internal/manual`) says "Bot computer" too; always-on prompts are size-tested (`prompt_budget_test.go`), so say it in few words.

# Computer is optional

A workspace may have no computer. `TOFI_COMPUTER_BACKEND=none|kvm` (unset: `kvm` when a computer socket is configured, else `none`; `cmd/tofi/accounts.go`)
decides it, in single and multi-account mode alike; `none` needs no Worker socket, provisioner or disk quota. `s.microVM == nil` is the server's one test for
it, exposed as `GET /api/computer/capabilities` and `computer` in `GET /api/config` (`{backend, available, attached, host_backend, capabilities}`, `computer_capabilities.go`; `backend`/`available` describe this account's attached computer, `host_backend` says whether the server can run one at all, so a detached account keeps the Attach surfaces: `useHostHasComputer`). Model-facing text
must not claim a computer when there is none: use the capability-driven variants (`taskCompletionGuidanceFor`, `onboardingSystemPromptFor`, `onboardingWelcomeFor`,
`scheduledFallbackGuidance`, `noComputerStatus`) and never add a computer sentence to an always-on prompt. The Web app reads `config.computer` through
`ui/src/computerCapability.ts` (`useHasComputer`) and hides every computer surface; Settings > Computer then lists how to add one. The web app never installs on the host (the one thing it may ask for is an update, which only the root host service performs: next section).
Design and record: docs/design/computer-optional.md (P0, P1 done).

First-run handovers (no model call): `GET /api/onboarding/handovers[?bot_id=]` (`internal/app/onboarding_handovers.go`) returns up to four `{id,passes,runs}` rows, and only while the account's primary Bot has `bot_onboarding.status='pending'` (else an empty list). The rows come from `eval/trust_tiers.json` (machine copy of the trust report, embedded by `eval/embed.go`, package `evaldata`): `tier=safe` only, every `needs` entry available now (`computer` = `s.computer() != nil`; `schedules`; `web_search` = the automation switch; `gmail` = `local_gog` usable; any OAuth MCP server by name when connected), the default model absent from `not_for`, ordered by Wilson lower bound then runs. Adding a task = a JSON row plus `chat.json` `firstrun.items.<id>.{label,message}` in all 7 locales; an id with no wording is left out by the UI. `ui/src/HandoverChips.tsx` (lazy; a quiet label and a wrapping row of label-wide L2 keys with the send key's press, no card and no footnote; one column of full-width keys on phones) renders in the pending Bot's first DM in place of the day-one templates card (`DayOneTemplates`), never with it; a click fills the composer (editable, focus moved) and sends nothing. The pending onboarding run (`context.go`, next to `onboardingSystemPromptFor`) also gets a `[proven handovers]` data block (`provenHandoversBlock`: up to six `kind | needs | touches` lines, same filter, no wording) and the prompt closes with one principle sentence naming it; the opening messages (`onboardingWelcomes`) ask one question, the work, and leave the name optional. Keep the first-turn onboarding text near 530 tokens. Tests: `TestFilterHandovers*`, `TestOnboardingHandoversEndpoint`, `TestOnboardingClosesWithProvenHandovers`, `npm run test:onboarding`.

# Computer size is set by the admin

Multi-account: only an admin sets an account's vCPUs, memory and disk, in Admin console > account (`AdminAccountDetail.tsx` `ComputerSize`, shared `ResourceSheet.tsx`), through
`GET|PUT /api/admin/accounts/{id}/resources` (`account_resources.go`; disk grows only, bounded by host free space, applied through the broker `quota` op `applyQuota`). A member's
`PUT /api/computer/resources` returns 403 `quota_management_required`; a member may read it and `POST /api/computer/resources/apply` (restart to apply what the admin saved).
Settings > Environments (the VM's Configure dialog) shows a read-only summary to members and a link to the console to admins; the single-account owner (the admin) still adjusts it there.

# Computers are providers and rows (computer-decoupling S5, S6)

`computer.Provider` (`internal/computer/provider.go`) is what the server holds; `*computer.Client` (Firecracker) is the only implementation. Optional interfaces (`Streamer`, `Resourcer`, `OAuthBridge`,
`RunnerHost`, `LegacyBlobs`, `Socketed`, `Healther`, `Heartbeater`) are type-asserted behind a capability. `s.computer()` is the account's VM or nil (`s.microVM` is its storage; write it only through
`AttachVM`/`DetachVM`, or directly in tests); `/api/computers/{id}/` resolves `{id}` through `Provider.ID()` (`isVMRoute`). Computers are rows in `computers` (`computer_rows.go`: id, name, kind `vm|personal`,
platform, region, labels, protocol_version, status `attached|lost|detached`, last_seen; one row is the VM, up to `Config.MaxPersonalComputers` (default 6, env `TOFI_MAX_PERSONAL_COMPUTERS`) are the person's own).
Each computer has a runtime slot (`computer_registry.go`) with its own operator lock (only one Bot at a time; a lease per tool call, released when the call ends and handed to the next Bot in line in arrival order; `releaseComputerHolds` is the end-of-run safety net), a call counter and a context. The VM keeps its
shared-desktop lease, keyed by the computer id. Bots reach other computers with `list_computers` and `computer_action{computer_id}` (registered only when a personal computer exists); the convenience tools act on the VM.
Hot attach/detach needs no restart: the administrator calls `POST /api/admin/accounts/{id}/computer/{attach|detach|state}` (gateway) or `/api/admin/computer/*` (single account; never served inside a gateway workspace).
`DetachVM` stops new calls (state draining), waits for running ones up to `wait_seconds`, copies the outbox to the server (`syncOutboxForDetach`), cancels what is left (those calls end with the tool error
`computer_detached`, effect unknown) and stores status `detached`, which a restart keeps until an attach. A computer with a `Heartbeater` that is silent for `computerLostAfter` is marked lost: its lock is freed and calls fail
with `computer_offline`. The administrator's answers contain the VM and the server only (`adminVMSummary`); never put a personal computer, its name or its count into an admin response or log. A run's computer use is recorded in `run_computers`
(run_id, computer_id, nullable region and compute_ms; a table of its own because three more columns on `runs` move the planner off `runs_active`; no UI yet). Tests: `computer_registry_test.go`, `computer_attach_test.go`, `computer_gate_test.go` (the release gate), `computer_upgrade_test.go` (data written by main).
The personal-computer pairing routes (`POST /api/computers/pairings`, `GET /api/computers/pairings/{id}`, `POST /api/computers/pair`) are on by default (owner, 2026-11-03: whether a person uses a personal computer is up to their desktop app). `TOFI_PERSONAL_COMPUTERS=0` turns them off: the routes answer 404 and Settings > Environments offers no Mac (`Config.PersonalComputers`, `computer.personal_computers` in `GET /api/config`); any value other than empty, `0` or `1` fails at startup. The Bot gets the Mac tools only while a Mac is paired.
Personal-computer worker, server side (N1, `personal_computer.go`): a Mac claims the one-time code (`POST /api/computers/pair`), keeps the device token (shape `<account id>.<secret>` in gateway mode, so `AccountGateway.deviceWorkspace` can route the session-less device routes to the issuing workspace; the id is only a routing tag, the secret is checked by the workspace) and then speaks only outward: `GET /api/computers/{id}/jobs?wait=N` (long poll, N <= 25 s), `POST .../jobs/{job}/result`, `POST .../heartbeat` (every 10 s), `PATCH .../capabilities`; these are the only owner-independent routes (`ownerIndependentRoute`), and each checks the token against its own `{id}`. Revoke is `DELETE /api/computers/{id}` (owner session): the token then answers 401 `device_revoked`, the slot is unregistered and calls in flight end as `computer_detached`. Every personal row gets a registry slot (`ensurePersonalSlot`, at claim and at start) whose provider (`personalProvider`) turns one `computer_action` into one `computer_jobs` row; so the per-computer lock, the lease per call and the review of `computer_action` are the same as for the VM. `shell.exec` is accepted as the name of `sandbox.exec`. A Mac silent for `personalLostAfter` (45 s) is marked lost by the sweep or by a waiting call: the call ends with `computer_lost` (effect unknown), open jobs are cancelled and never replayed, new calls get `computer_offline`; the next heartbeat attaches it again. Whether a Bot may use a Mac is decided on the Mac (its per-Bot allow-list and folder grants), not by the server; the claim answer carries `bot_id` and `bot_name` for that. The owner's test endpoint `POST /api/computers/{id}/actions` accepts an optional `bot_id` (an existing Bot) so a job can be attributed without a model run; without it the Mac refuses the job. `TestPersonalMacEndToEnd` and `TestPersonalMacRefusedBotAndLostMac` run the real Mac worker (a tofi-app checkout, `TOFI_APP_DIR`; skipped when unset) through `computer_action`. The admin surface never lists, counts or names a Mac (`TestAdminCannotSeePersonalComputers`). The flag `TOFI_PERSONAL_COMPUTERS` still gates claim and code issue and is off by default.
Personal-computer liveness and approvals: a device is online only if it polled or beat within `computerOnlineWindow` (60 s), in `GET /api/computers`, `list_computers` (online first) and `botComputers`; `computer_action` on a silent device fails with `computer_offline` and names the online ones. `computerActionOn` runs `guardPersonalAction` (the VM's `guardAction`) and fails closed on the person's own machine: `desktop.click/double_click/triple_click/drag/scroll/type/key` with no `args.effect` are reviewed as consequential, effect `none` skips the review, `desktop.move` and `desktop.capture` are never reviewed (the effect field is stripped before queueing); `files.write`/`sandbox.exec` are always reviewed; reads are not gated. Compose passes `TOFI_PERSONAL_COMPUTERS` and `TOFI_MAX_PERSONAL_COMPUTERS`.
Personal-computer desktop vocabulary (`computers.go`, `personal_desktop.go`): a Mac speaks the VM's names: `desktop.capture` (`screen.capture` is the older name, aliased both ways: the job carries the name the device declared, `deviceActionName`), `desktop.click/double_click/triple_click/move/drag/scroll/type/key`; coordinates are pixels of the last capture, the Mac maps them to points. A device that grants `desktop.click` also serves double/triple click, move, drag and scroll (`grantedAction`, as the desktop app does). Result limits stay 1 MiB / 768 KiB picture; a `desktop.capture` result gets the `screen.capture` image checks. `computer_desktop` has an optional `computer_id`: absent = the Bot computer as before; a personal computer id translates to the vocabulary above (`personalDesktopArgs`) and goes through `computerActionOn`; `start/stop/trace` are Bot-computer only, `move/drag/button/to_x/to_y/display` Mac only (refused, not dropped, on the Bot computer). A personal capture is not kept in the work trace. `computer_action` stays for `files.*` and `sandbox.exec`. An account with no Bot computer (no VM) whose paired Mac declares a desktop capability still gets `computer_desktop` (`personalDesktopTools`); with exactly one such Mac it is the default, with several the Bot must pass `computer_id` (the error lists them); with a VM the default stays the VM. `computer_action` runs the offline check for personal computers only. The Mac's refusals map to typed outcomes in `personalJobError` (always the server's wording, never the Mac's text): `bot_not_allowed` (person must allow the Bot in the desktop app's Mac Device Settings; stop), `user_stop` (certainty unknown), `user_paused`, `user_takeover` (no automatic retry; tell the person), `secure_input` (never type secrets; ask the person), `capability_not_granted` (names the capability and the setting; also the server-side check). The `computer_desktop` description stays within 1024 bytes (`TestBuiltInToolDescriptionsFitProviderLimit`; `computer_action` was already over before this and is not made longer), so the per-kind action list lives in the `computer_id` parameter description and the description only points at it.
Sharing a Mac capture (`personal_desktop.go`, design `background-computer-use.md` section 5): `computer_desktop` `capture` with `share: true` on a person's own Mac keeps that one picture as a `published` attachment (`addAttachmentOpts` then `stageRunAttachment`, bound to the reply by `bindRunAttachmentsTx` like `publish_file`) and adds `shared {attachment_id,name,url,attached_to_reply}` to the result; `share` on any other action or on the Bot computer is `invalid_arguments`. Without `share` the picture is not kept. A capture result for the model carries `image_visible_to_you: true` (formerly `image_attached`, which read as delivered to the person) and, on `computer_desktop`/`computer_browser`, `shared_with_person: false` unless `shared` is present (`agent/vision_tool.go`). `guardShare` asks the Mac owner with a D72 card only when `conversationHasOtherPeople` is true; it is `false` today because a conversation has one person and Bots (`members` lists Bots), so no card appears until a conversation can hold another person. `workspace_capabilities` with `query` answers `no_close_match: true` (plus `nearest` names, nothing loaded) when no tool is ranked or the best one covers under half the query terms (`queryFits`, `extensions.QueryCoverage`). A Mac's `screen_permission_pending` (capture without Screen Recording access) is worded by `personalJobError` as a person-only question: no retry. The Q1 note (macOS re-asks about screen access; choose Allow) is `environments.rc.screen_prompt` in the seven locales and in the Mac app's confirm dialog. A left click result carries `via` (`ax_press` or `pointer`).
Computer configuration (computer-decoupling S2): the Keys page, `ComputerContents` ("What is on this computer": browser sign-ins, installed tools, work files, environment and keys, in words that say they are lost with the computer) and the wipe list `ComputerLossList` (names and counts from `GET /api/computer/contents`, `internal/app/computer_contents.go`) exist only while `useHasComputer()`; with no computer the web app makes no `/api/computer/*` request (`test:no-computer` holds it). `[run context]` adds `freshComputerStatus` while nothing is saved in Settings for the computer. `tofi computer remove --purge` prints the same class C list (`computer_loss_lines` in `tofi_host.py`). `tofi computer add|remove` call the App's host route (`/api/host/computer/{state|attach|detach}`, `host_control.go`; bearer token in `data/host-control.token`; served only to a loopback or container-gateway peer, any other source gets 404; Caddy answers 404) so the App is not restarted; 404/401/409/no answer falls back to the restart (`HostControlUnavailable`). While the host has the computers off, the gateway's `provisioner()` is empty (no reserve/ensure/reclaim) and new workspaces start with `ComputerStartDetached`.

# Environments and the E2B computer (docs/design/environments.md)

Settings > Environments (tab id `computer`; `devices` deep links land there; Keys moved to the Advanced group) reads one aggregated `GET /api/environments` (`environments.go`): the Bot computer, an E2B computer that is set up but not in use, and paired Macs, each with `state`, `access` (`all_bots`, `allowed_on_mac`, `none`) and the `actions` the page may offer. An account has at most one Bot computer, the VM or the E2B computer; it always sits in the VM slot under `computer.DefaultID`, so `/api/computers/firecracker/*`, the shared-desktop lease and recovery identities need no case for the kind, and the `computers` row of that id carries the current kind's name and capabilities (`botComputerRowLabel`). `PUT /api/environments/e2b {api_key, template_id?}` checks the key (`GET /v2/sandboxes`), seals it (vault kind `computer_provider`, ids `computer:e2b` and `computer:e2b:guest`; never listed or applied by the Computer credentials routes, `TestE2BSecretsStayOutOfTheCredentialsList`) and builds the template in the background; with no Bot computer the E2B computer attaches when ready. `POST /api/environments/{firecracker|e2b}/use` switches with `DetachVM` (drain, outbox copy) and `attachProvider`; the choice is the automation value `environments.bot_computer`, honored at start-up (the VM is not attached when it is `e2b`; `fallBackToVM` attaches it when the E2B computer cannot be restored). Non-secret E2B state is the automation value `environments.e2b`. Capabilities follow the kind (`computerCapabilities`: E2B lists no `resources`, `mcp_runner` or `oauth_bridge`).
The E2B computer runs our Guest: the release job `e2b-image` (non-blocking, `continue-on-error`) pushes `ghcr.io/jackzhao98/tofi-worker:<tag>-e2b` (a tag on the public package; a new GHCR package would start private); the server builds the template `tofi-computer-<version>` (2 vCPU, 4 GiB) from it in the person's E2B team, or uses a `template_id` the person built (`CustomTemplate`, never rebuilt). Source builds have no image unless `TOFI_E2B_IMAGE` is set; `TOFI_E2B_API_BASE` points tests at a fake. In the sandbox `tofi-guest --listen tcp://0.0.0.0:8331 --token-file /var/lib/tofi/guest-token` (`deploy/e2b/start.sh`) requires the bearer on every route but `GET /health`; sandboxes are created with `allowPublicTraffic=false`, so calls also carry E2B's traffic token. The server writes the token through envd and proves it with an authenticated call (`provisionToken`; root first, then the uid 1000 user). Sandboxes auto-pause after `computer_idle_off_minutes` idle minutes (E2B keeps memory and disk; default 15, 5-60 because E2B's Hobby plan caps a timeout at one hour; `Provider.SetIdleTimeout` gives a running sandbox a changed value at once) and resume on the next call. The power button in the computer window (`POST /api/computers/firecracker/sleep`, shown when info has `can_sleep`, E2B only) pauses it now and refuses with `computer_busy` while a call is in flight or a run or the person holds the desktop (`computerInUse`: the signals `DetachVM` waits on). The window wakes a hibernated computer only when it opens, or on the power button or the off screen's Turn on: waking it on every turn to hibernated kept an open window's computer running. A sandbox of an older template is never replaced silently either: `Prepare` keeps it, `Status()` reports `GuestOutdated`, `GET /api/environments` offers `upgrade` on the e2b item and `POST /api/computers/firecracker/upgrade` replaces it on the person's request (files removed; see "User groups and organization resources (slice 3)"); a sandbox stored before the version was recorded counts as outdated but stays usable. The own-key template is built only by `Prepare` (adding the key or finishing an interrupted build), so an own-key sandbox reports outdated once a newer template has been built. The template's phase is separate from the computer's (`TemplatePhase`): a build or a failed build gates only creating a sandbox. A sandbox that vanished on E2B is never replaced silently: the computer reports `sandbox_gone` and Retry makes a new one (owner rule: no fallback without consent). Sandbox URLs must be on `e2b.app`/`e2b.dev` with the default API base. An organization can provide the E2B computer instead of the person's own key (`provided/e2b`, "User groups and organization resources (slice 3)"): the template is built once by the gateway, each account gets its own sandbox with an `account` metadata marker, and the key never reaches a member. `deploy/e2b/smoke.sh <image>` checks an image on an x86_64 Docker host.

Remote control this Mac (environments-simplify.md P0, owner decisions D80): in the Mac app, Settings > Environments has one switch "Remote control this Mac" instead of a pairing code. The page (`ui/src/RemoteControl.tsx`, `useRemoteControl.ts`) only asks `window.tofiDesktop.remoteControl` (`status`, `set`, `authorize`, `stop`, `relaunch`, `deniedBots`, `undoDeny`, `onStatus`; types in `desktop.ts`). The app's main process answers workspace documents only, shows the native macOS confirmation for `set(true)` and pairs silently with the session (the same two routes, `POST /api/computers/pairings` then `/pair`; the code never reaches the page; no server change: `originOK` lets a request without `Origin` through, and the pair route still needs one capability, so the switch can wait for macOS permissions). Turning off calls `DELETE /api/computers/{id}`; a Bot then gets `computer_detached`. A result is `{ok, code?, status}`; every failure code has its own sentence in the 7 locales (`environments.rc.reason.*`). The Mac's own device is shown once, as the "This Mac" row in the block above the list (state dot + word, one reason sentence, one text action, a "⋯" menu with "Files and local execution" and "Bots denied on this Mac"); `EnvironmentList` skips the server row with `deviceID`. No `remoteControl` bridge (a browser, an older app) = no switch, one paragraph on how to add a Mac. `MacDialog`, the "Your Mac" Add item, `ThisMacCard` and the pairing code UI are gone. The Mac settings page (`/__desktop/settings`, `ui/src/desktop-settings/`) is now "Files and local execution", marked In development, reached from the this-Mac row's menu; it also carries the same switch block at the top (no menu there), because a new app on an older server has no switch in its workspace and that server's Add > Your Mac dialog only offers "Open Mac settings" (the app answers `remoteControl` from this document too); it has no pairing, screen or control switch, macOS permission or Bot list. While the switch is on every Bot of the person may use the Mac on the Mac side; only an older local "deny" vetoes (undoing one asks in a native dialog). The server's `bot_not_allowed` wording (`personalJobError`) still says to allow the Bot in "Mac Device Settings", which no longer lists Bots: P2 changes it with the per-Bot server switch. The list's full restyle is P1; the Bot-settings toggle and server-side reasons are P2.

# Update from the web page

The Version card (Settings > System) and the banner have an **Update to vX** button for admins (decision D69, `docs/decisions/0069-web-update-request.md`). The web app only
REQUESTS: `POST /api/system/update/request {version, channel}` (`internal/app/update_request.go`) checks that the version is the cached latest stable (or the newest rc when the
root-server setting `update_channel_rc` is on, `PUT /api/system/update/settings`), then writes `request.json` atomically (temp file + hard link, so only one can be pending) into
`TOFI_UPDATE_REQUEST_DIR` (`/update/request` in the container = `/var/lib/tofi/update-request`, the only App-writable host directory, uid 10001). `tofi-update-request.path`
(PathExists) starts `tofi-update-request.service` as root, which runs `tofi update --from-request` (`update_from_request` in `deploy/self-host/tofi_host.py`): it reads the file as hostile
input (O_NOFOLLOW, regular file, 4096 bytes, exact keys `version, channel, requested_at, nonce`, release-tag regex, age <= 1 h, nonce seen once), refuses downgrades, an rc tag on `stable`
and the reverse, a stable version other than `releases/latest`, an unpublished release (manifest not fetchable), a version rejected here before and any schema change, then calls the same
`upgrade()` as `tofi update` (wait up to 60 min for Bot runs, backup, digest/sha256 checks, rollback; trigger `web` in `update-history.jsonl`). It writes `status.json` atomically into

# OpenAI-compatible endpoint

A fourth provider card, `openai_compat` (public id `compatible`, label "OpenAI-compatible"), points the agent loop at a server the admin names: Ollama, LM Studio, vLLM, OpenRouter and the like. Settings are `PUT|DELETE /api/providers/compatible/config {base_url, key?, models?}` (`internal/app/compat_provider.go`); `POST .../models` lists the server's `/v1/models` without saving. Base URL, optional key and typed model IDs are sealed together in the vault record `provider:openai_compat`; the key is shown only as `key_hint`, and a blank key keeps the stored one only while the address is unchanged. Model IDs carry the prefix `compat:` (`provider.CompatModelPrefix`), which routes them (`ProviderForModel`) and is removed before the request leaves (`provider/openai_compat.go`). The wire format is Chat Completions with tool calling and streaming (the Responses API is not required by the agent loop); a missing tool-call id is made up, a call index that starts above 0 is accepted. The window is what the server reports (`context_length`, `max_model_len`, `context_window`, `max_context_length`, `meta.n_ctx_train`) through `provider.SetCompatContextWindows`, else the existing 500k heuristic (`window_known:false`). Cost is unpriced (`CalculateCost` knows no `compat:` row), so the Usage page counts such requests as unpriced, never invents a price.

Ollama is the first-class case (card preset "Ollama" fills `http://host.docker.internal:11434/v1`): no key is needed and no Authorization header is sent for an empty key; when `{base}/models` fails the list comes from Ollama's `GET {root}/api/tags`; when `GET {root}/api/version` answers like Ollama, each model's window is read from `POST {root}/api/show` (`num_ctx` from `parameters`, else `<arch>.context_length` of `model_info`; at most 50 models, 4 at a time) because the window Ollama runs with, not the model's maximum, is what the Bot can use. A stream that numbers several complete tool calls with the same index (Ollama) is split by call id. The App container reaches a host Ollama through `host.docker.internal` (both compose files map it with `extra_hosts: host.docker.internal:host-gateway`, so Linux works too) or the host's LAN address, and Ollama must listen on all interfaces (`OLLAMA_HOST=0.0.0.0`); its default context is small, so the card tells the admin to set `OLLAMA_CONTEXT_LENGTH` (or `num_ctx` in a Modelfile). First-run setup has the same option ("Ollama or your own server", lazy `OnboardingServer.tsx`: Ollama preset, optional key, test connection, model pick, Connect); `endpoint_not_allowed` there names `TOFI_ALLOW_PRIVATE_ENDPOINTS=1`. Tests: `TestCompatOllama*`, `TestCompatOllamaStreamsParallelCallsOnOneIndex`, `npm run test:compat-provider`.

SSRF rule: the request leaves the App server for a host the admin typed. Loopback, private (RFC 1918, ULA) and carrier-grade NAT addresses are reachable only when the account's user is currently a server Admin (the gateway passes `Config.AccountIsAdmin`, a live read of `accounts.role`, so a demotion applies on the next check), for a workspace without a gateway (`s.accountID == ""`), or when the operator sets `TOFI_ALLOW_PRIVATE_ENDPOINTS=1` (passed through all three compose files; set it in `/etc/tofi/tofi.env` and restart); a member cannot aim the server at its internal network. Link-local (cloud metadata), unspecified and multicast addresses are never reachable. `TOFI_ALLOW_PRIVATE_ENDPOINTS=1` is the general flag for models and MCP; `TOFI_ALLOW_PRIVATE_MODEL_ENDPOINTS` still works as a model-only alias (it does not open MCP). Bot-managed MCP servers keep the full `GuardedTransport`. Stdio and local plugin MCPs (`account-computer`) do not use this path. The owner transport ignores proxy variables. Tests: `extensions/home_assistant_test.go` (Admin reaches LAN, member blocked, link-local never), `spend_review_test.go` (`TestMCPEndpointRuleForMemberAndAdmin`). The rule is checked when saving (`compatHostCheck`) and again on every dial (`compatDialControl`, so DNS changes and redirects meet it), and the client ignores proxy variables. Tests: `compat_provider_test.go`, `provider/openai_compat_test.go`.

- Redaction (design 4.8), three layers. (1) `provider.RequestFailure` wraps every `client.Do` error of the OpenAI, Anthropic and compatible providers without the URL or host:port (only the operation and the cause stay). # User groups and organization resources (slice 3: the organization's E2B computer)

`provided/e2b` is one E2B team owned by the organization (`internal/app/org_e2b.go`; provider changes in `internal/computer/e2b`). The cloud instance has no VM, so this is how its members get a Bot computer. `computerUsesOrgE2B(v)` is the separate allowance (`computerAllowsVM` and `computerAllowsOwnE2B` stay false for it): under it `restoreE2BEnvironment` and `enforceComputerPolicy` attach the organization provider (`attachOrgE2B`, even with no key or a failed build, so the computer reports the named code and Retry reaches it), `environmentsView` lists only that computer (`orgE2BEnvironmentView`), and the own-computer writes stay 403 `managed_by_organization`.

- S4 split. Organization part: the key (org vault `computer:e2b`), `org_resources['computer:e2b'].config` = `{template_id?, build?}` (`template_id` is a template the admin supplied, used as it is and never rebuilt; `build = {template_id, build_id, version, phase, error_code, updated_at}` is the build the server made). Workspace part (`orgE2BStore`): the sandbox id, phase and error under the automation value `environments.e2b_org`, and the guest token under the vault id `computer:e2b-org:guest`. Own-E2B workspaces keep `e2bStore` (`environments.e2b`, `computer:e2b:guest`) unchanged and the two never share an id, so a person's own sandbox is never handed to the organization's key. The provider gets `Config.KeySource` (the key is asked for at each request through `Config.OrgCredential`, never held), `TemplateSource` (`AccountGateway.orgE2BTemplate`, read before every `ensure`/`Info`/`Retry`; `Provider.Status()` separates the computer's phase from the template's: `Phase` is the sandbox's, `TemplatePhase`/`TemplateErrorCode` are the image's, and a template that is not ready becomes `Phase` only while there is no sandbox, because the template gates `create` and nothing else), `SandboxMetadata` (`account: <id>`), `OnKeyRejected(usedKey)`, `OnUsage`, `Scrub`, `MinGuestVersion`. A provider with a `TemplateSource` is member-facing: its API client replaces upstream error text by text we make (`memberText`: status and code only) and also scrubs the current template and build ids, so a member (the view, `Info.Error`, retry/wake/upgrade answers, tool results) never reads the organization's template, build or team in E2B text.
- Template: built once per organization and TOFI version (`tofi-computer-<version>`) with the org key by the gateway (`kickOrgE2BBuild`, `runOrgE2BBuild`; a mutex-guarded run per generation, so any number of first uses start one build; `Close` cancels and waits). A failed build stays failed until the admin retries it (members do not each retry), a build cut short by a restart starts again at the next use. `orgE2BReset` (under `orgWriteMu`, from a key PUT, a DELETE or a retry) bumps the generation, so a build of an older key can no longer write state. A PUT of the key also starts the build at once. The admin view: `orgResourceView.build = {phase: none|preparing|ready|failed, custom, version, error_code?, updated_at?}` (computed from the row; `none` is "not built for this version yet"). The build code is a code only (`template_build_failed`, `image_missing`, `invalid_key`, `e2b_unreachable`...). A sandbox is never removed when the template version changes: while the next version builds, and after that build fails, `ensure`/`Info`/`Retry` go on against the existing sandbox (a missing key is still `org_resource_missing` from the API call). Template upgrades keep the sandbox with consent to replace (next bullet). `Close` and a timeout-free cancel never persist `failed`: `Prepare`'s `failed` returns `ctx.Err()` when the context was canceled (the state stays `preparing`, the next use resumes), and `stopOrgE2BBuilds` bumps the generation so no write after `Close` passes. Adoption: E2B's `POST /v3/templates` registers a new build on the team's own template when the name is posted again (e2b-dev/infra `template_request_build_v3.go`: same team and alias reuse the template id; a 409 is a race that says "retry the template build request" or a name taken by a template id; the OpenAPI lists 409 without detail), so when the adopted template's newest build is in error the provider posts the name once more and builds on it; if E2B still answers 409 the code is `template_stale_in_team` (only the team's owner can clear that template in E2B). Admin view `build.min_guest_version` shows the server minimum. Counting accounts still on an older template is not shown: it lives in each workspace's own state, which the gateway cannot read without loading every workspace.
- Template upgrades (decision 11-08): a sandbox records the template it was made from (`orgE2BSandboxState.template_version`: the TOFI version, or `custom:<digest of the template id>`; the id itself never goes into a workspace). When the ready template differs (or none was recorded) `Status()` has `GuestOutdated`, `computer.Info.guest_outdated` is true, the computer stays usable and `GET /api/environments` offers `upgrade` on the e2b item (`guest_outdated: true`; `e2b.guest_outdated`, `e2b.template_phase`). `POST /api/computers/firecracker/upgrade` (member, policy must allow the org or own E2B computer; 409 `computer_busy` while in use; 409 `not_outdated`) does `Remove` + `create` from the ready template (never when the new one is not ready: nothing is removed for a template that cannot be made); the same consent as `sandbox_gone` then Retry, and the files on the old sandbox go. `TOFI_E2B_MIN_GUEST_VERSION` (default unset: not enforced) sets `minGuestVersion`: a sandbox below it (an unknown version counts as below; `custom:` ones are exempt) is refused by `ensure` with `guest_outdated_required` (fail closed), shown as `failed` with that code and only the `upgrade` action, until the member upgrades. Version order is `e2b.VersionBelow` (semver core, a release candidate is below its release; unreadable text is below). The org-level "force by deadline" setting is a later phase.
- Sandboxes: one per account, created by the member's workspace with the org key; metadata `{app: tofi, account: <account id>}`; auto-pause, resume, Retry and the power button work as before (`computer_idle_off_minutes` is the member's; `applyE2BIdleTimeout` reaches the organization provider too); `sandbox_gone` is reported and never replaced silently.
- Never leaves the server (design 4.8, `TestE2BSandboxGetsNoOrgSecret`): the key is only the `X-API-Key` header to the E2B API; the create request has no environment; the only write into a sandbox is its own guest token; envd and traffic tokens stay in the provider's memory; the desktop stream is proxied. E2B error text is scrubbed (`Config.Scrub` masks every 8-character stretch of the key). No fallback: a missing org key or a failed build is `org_resource_missing` or the build's code, and the member's own E2B key is never used (the own provider is not even built under `provided/e2b`).
- Policy moves: into `provided/e2b` the own computer (VM or E2B) is detached through `DetachVM` and the organization's attached; out of it the computer is detached, the sandbox paused, and where the new policy allows one the person's own E2B computer (`restoreE2BEnvironment`) or the VM (`AttachVM`) comes back. `attachOrgE2B` re-checks the policy after attaching. `GET /api/environments`: `policy = {mode: provided, source: organization, via: e2b}`, `e2b = {configured, phase, error_code}` (no key hint, no upstream text), one `e2b` item (state `preparing|asleep|ready|starting|resuming|failed`, `bot_computer`, actions at most `retry`; no `use`/`remove`), `add.e2b=false`. `GET /api/config.capabilities.computer = {mode: provided, source: organization, via: e2b}`.
- Usage: `org_usage` has `compute_ms` (added by `ensureOrgUsageColumns`; `OrgUsageEvent.ComputeMS`). It is the provider's own accounting of sandbox running time (`e2b.Provider.OnUsage`), because `run_computers.compute_ms` is the wall time of a call and is not recorded for the Bot computer slot at all. Time accrues from create or resume, is reported about once a minute while the sandbox is used, and at the stop: a pause or kill ends at that moment, a stop nobody saw (E2B paused it after the idle timeout) ends at the last refresh plus the timeout, and `Server.Close` settles a sandbox left running (`Settle`). Short flaps of the "running" flag lose a few seconds at most.
- Rejections: an E2B 401 or 403 to a team-level request made with the org key (a sandbox create or a template call; not a per-sandbox call, which says nothing about the key) records `status=rejected, error_code=invalid_key` through `Config.OrgResourceOutcome`, and only when the request carried the key in force now (`orgE2BKeyRejected`, `rejectOrgE2BKey`: an older key or a build of a past generation is ignored).
- Cleanup: account deletion's `computer` step first lists the organization team's sandboxes with the marker `account=<id>` (`e2b.RemoveAccountSandboxes`, `GET /v2/sandboxes?metadata=account%3D<id>&state=running,paused`, each row re-checked for `app=tofi` and the account) and kills them, best effort and logged by code (`reclaimOrgE2BSandbox`); it finds the sandbox without the workspace being deleted, so a retried deletion works too. - Test seams: `e2bHostURL` (where the guest and envd of a sandbox are reached) and `e2bNow`. Fake: `orgE2BFake` in `org_e2b_test.go` (the E2B API, envd and the guest in one server, via `TOFI_E2B_API_BASE`); seed the org key with `seedOrgE2B` (a PUT starts a build).

- Tests: `org_e2b_test.go` (`TestE2BSandboxGetsNoOrgSecret`, `TestOrgE2BTemplateBuiltOncePerOrg`, `TestOrgE2BSandboxPerAccountWithAccountMetadata`, `TestProvidedE2BWithoutOrgKeyFailsNotFallsBack`, `TestPolicyMoveIntoAndOutOfProvidedE2B`, `TestMemberCannotChangeOrgE2B`, `TestOrgE2BUsageAttributed`, `TestCapabilitiesReportProvidedE2B`, `TestOrgE2BBuildFailureAndAdminRetry`, `TestOrgE2BKeyRejectionIsRecorded`, `TestOrgSearXNGClientIsBoundToItsHost`, `TestReviewerFailureLogIsScrubbed`); review fixes in `org_e2b_review_test.go` (`TestOrgE2BExistingSandboxSurvivesNewTemplateAndUpgradeNeedsConsent`, `TestOrgE2BMinimumGuestVersionRefusesUntilUpgrade`, `TestOrgE2BBuildOfAReplacedKeyCannotWrite`, `TestOrgE2BCloseLeavesTheBuildResumable`, `TestOrgE2BGuestTokenOfAnotherAccountIsRefused`, `TestOrgE2BKeyRejectionNeedsTeamLevelCallAndCurrentKey`, `TestMemberViewsCarryNoOrgTemplateOrBuildIds`, `TestAccountDeleteReclaimsOrgE2BSandbox`, `TestOwnE2BComputerKeepsItsSandboxOnANewTemplateUntilUpgrade`) and the provider cases in `internal/computer/e2b/provider_test.go`; `TestOrgSecretNeverInMemberResponses` also runs the E2B paths.

## Conversation usage

`GET /api/conversations/{id}/usage` (`internal/app/conversation_usage.go`, same owner session gate as `/tools`; unknown conversation is 404 `not_found`) reads existing rows only; nothing new is stored. `totals.input_tokens/output_tokens` are summed from `run_usage` (no expiry; includes reviewer calls). `requests`, `equivalent_usd` (`usageEquivalent`: the Codex reference table with cached input at 0.1x, otherwise the `provider.Registry` price by prefix so dated Claude and OpenAI API IDs are priced, cache reads/writes at their own rates; plus web-search fees, $0.01 each, web fetch free) and `unpriced_requests` come from `usage_calls`, which `pruneUsage` keeps seven days, so they cover only runs whose per-call rows add up to the run totals (`runs_with_call_detail` vs `runs`). `latest_context` is the newest `run_usage` row of the conversation: `used_tokens` is the provider-reported input of its last call (`used_measured:true`), else the pre-call estimate; `window_tokens` is the stored window (`provider.GetContextWindow`: the window the Codex `/models` catalog reported (`context_window`, else `max_context_window`; `publishCatalogWindows` -> `provider.SetCatalogContextWindows`, also warmed from the stored catalog at start) outranks the `Registry` row, which outranks the 128k heuristic; `window_known:false` means heuristic and the UI shows it as estimated; a stored heuristic window is re-read live in `latestContext`), `cache_read_tokens` / `cache_hit_rate` are the last call's prompt-cache reads over its input (`run_usage.last_cache_*`; `totals.*` use `total_cache_read` over `total_cache_input`, the input of calls whose provider sent cache fields at all, `provider.Usage.CacheReported`; the rate is `null` when none did, never 0; Responses/Chat Completions read `cached_tokens`, Anthropic its cache fields); `parts` regroup that run's snapshot (first call only, on-demand parts excluded) into `instructions, history, tool_definitions, tool_results, memory_notes, attachments, other`, all estimates (`agent.EstimateTextTokens`; images are the flat `contextImageTokens` taken out of their history message into `attachments`; text attachments stay inside `history`). `usageGroupOf` maps kinds, and an unknown kind lands in `other`. A missing snapshot gives empty `parts` with `parts_code: context_snapshot_unavailable`. `tool_split` classifies each chat model call by whether the run started a tool (`tool_activities.started_at`) between that call and the next one (usage is recorded before tools run); reviewer calls are `review_tokens`, in neither side. It is `available:false` with `code` `no_usage` or `call_detail_incomplete` rather than a guess. Tool-result tokens that arrive mid-run are not in the snapshot (first call only), and per-call input repeats history, so the split says where calls were spent, not what text cost.

Monthly spend cap (item #9, `internal/app/spend_cap.go`, `spend_admin.go`; UI `SpendCap.tsx`, `AdminSpend.tsx`, `settings/spend-cap.css`). # Notifications (server-side events)

Phase 1 of the notification design (D78; design `cloud-services.md` 4.1, phase 2 in `cloud-services.md` section 10). The server, not the web client, decides what needs a person's attention, and writes one pointer row per event into `attention(id AUTOINCREMENT, kind, detail, conversation_id, bot_id, message_seq, created_at)` in each workspace database (`internal/app/attention.go`; `migrateAttention`; no text is stored, the content is read from the conversation API). `classifyAttention(attentionSignal)` is the one decision point and returns a kind or `""`: `reply` (an assistant message, not internal, in a conversation the list shows: visible and not archived), `task_result` (the same, kind `forward_result`: a delegation or scheduled-task result returning to its origin), `needs_you` (a run stops on a question or approval card and a person is the one to act), `spend_alert` (the monthly spend crosses 80% or the cap). The message conditions copy the web client's rule in `App.tsx` `refreshConversations` and the list SQL in `ListConversations`: `internal` is the list's own test (the message's run started in another conversation, except kind `user_message`), and kinds `bot_result`, `scheduled_task` and `internal` are never listed, so they never notify (`bot_result` is a private anchor for the sender's follow-up, so the design table's "bot_result" row is unreachable in the web client and is not a `task_result`). A row is written in the same transaction as the change: `recordMessageAttentionTx` right after each `INSERT INTO messages` of Bot speech (`finishRunOpts`, `publishAssistantTurn`, `publishSay`, chat segments, display cards, `appendForwardResult`, the Bot-to-person message, visible delegations, failed-run files, `AddMessage`), `recordNeedsYouTx` in `SaveInputContinuation` (the run's wait is saved; it records only if the question is still pending and no non-shadow automatic review is deciding it: in auto mode the gate blocks until the verdict, so a run stops only on a card the reviewer sent to a person, while an auto-approved or denied card never makes a row; ask mode, plain questions and shadow mode record at once), and `postSpendAlert` once per month, limit and threshold (`spend_alerts` percent 80 and 100; a call that crosses both writes one row; `detail` is `spend_warning` or `spend_cap`, null for other kinds; the warning row points at the note in the Primary Assistant's DM, the cap row has no `message_seq`). A message nobody posted has no row, and there is no second quiet rule. System notices (resume, handoff, settings change, command exit, onboarding) are not classified. `GET /api/notifications?after=<id>&limit=<n>` (`routeNotifications`; default 50, max 200, 400 `invalid_cursor` / `invalid_limit`) returns `{notifications: [{id, kind, conversation_id, bot_id, message_seq, created_at}], next_after}` for the signed-in account's own workspace database (in accounts mode each account has its own file, so no row crosses accounts). There is no live signal yet: a client reads `GET /api/notifications` with its `next_after` cursor (a `workspace_events` scope was tried and dropped, because the web client discards unknown scopes before advancing its cursor and a busy account would push that cursor out of the 128-row event window). The daily retention pass of the wait sweeper deletes rows older than 30 days (`runAttentionRetention`); deleting a conversation or Bot deletes its rows; the table is not exported. Phase 2 (server and web; the Mac app is a separate repo, `contracts/notifications-delivery.md` is what it builds against) adds the delivery view to the same route, in `internal/app/attention_delivery.go`. `GET /api/notifications?view=delivery` returns `{items, next_after, language}`; without `view` the body is the phase 1 one, byte for byte (`TestNotificationsWithoutViewKeepTheP1Bytes`). `deliverable(rows, before, facts)` is the only rule point of phase 2 and is pure; the HTTP layer only reads the facts (`deliveryFactsFor`: account switches, `conversation_reads`, titles, Bot names, pending cards, previews). Its rules: a kind whose account switch is off is dropped (`notify_chats` -> reply, `notify_tasks` -> task_result, `notify_needs_you`, `notify_spend_alerts`, all default on, in `user_preferences`, the settings registry as `account.notify_*`, `PUT /api/preferences`); a row with `message_seq` at or below the conversation's `read_seq` is dropped; a `needs_you` row is dropped when the conversation has no pending question on a `run_input_waits` row in state `waiting`; a row of a deleted conversation is dropped; the rest merge into one item per (kind, detail, conversation) with `count`, `id` of the last row; `quiet` applies to reply and task_result only (needs_you and spend_alert are never quiet) and is true when a deliverable row of the same conversation (any kind, from this response or, through `attentionContext`, from before the cursor) is up to 30 s older than the item's first row (stateless, `created_at` only); `title` is the conversation name, `bot_name` the Bot, `preview` the web client's `previewText` rule in Go (`attentionPreview`, 160 characters) for reply and task_result only, empty when the request says `content=0`. Fixed sentences (needs_you, spend alerts, "new message") are the client's, in the account language. Filtered rows still move `next_after`. `tail=1` returns no items and the highest id ever issued (`sqlite_sequence`, so a cursor survives retention emptying the table). `wait=<s>` (cap 25, `attentionMaxWait`) is `waitForAttention`, modelled on `waitForJob`: a primary-key probe every second, 2 s settle after the first row (`attentionSettle`; tests shorten it with `fastPoll`), context cancellation writes nothing; at most 4 waiters per workspace (`Server.attentionWaiters`), the fifth gets 429 `too_many_waiters`. `/api/server-info` (single and accounts handlers) carries `notifications: {delivery: 1, max_wait: 25}`; a client sends no delivery request to a server without it (owner decision Q15: it names "the server needs an update to send notifications", no fallback to an old rule).

# Search palette

The sidebar has no search field: a magnifier button (`.search-trigger`, in the entry) and Cmd/Ctrl+K open `ui/src/SearchPalette.tsx`, a lazy chunk (`searchPalette` in `lazyPanels.tsx`, warmed first in idle time and on pointer-over of the button) on `ModalDialog` in `#tofi-layers` at `--z-dialog`. All its state is local, so typing never renders the workspace. Chats are filtered from the loaded list; messages come from `GET /api/search?q=&kind=all|chats|messages&limit=` (`internal/app/search.go`, owner session gate like the other conversation routes), debounced 150 ms with the older request aborted. Enter on a message calls `openMessage` (the `taskFocus` jump; `keepJump` in `App.tsx` holds it through the first 900 ms of a conversation opening, and the flash is the `data-jump-target` attribute, not a class, because React rewrites the block's className). No `backdrop-filter` on its scrim: it made each key 72 ms to paint instead of 32 ms.

Index: `messages_fts`, a standalone FTS5 table with the `trigram` tokenizer (case-insensitive substring match; Chinese, Japanese and Korean match with no segmentation), keyed by message id through `search_message_ids` and kept by three triggers (`migrateSearch`, additive and idempotent; refilled when new, when an older external-content index is found, or when its row count drifts from `messages`). It is deliberately not an external-content table on `messages.rowid`: that rowid is unstable (TEXT primary key, VACUUM) and a purge that emptied the shadow tables corrupted the file. `purgeWorkspaceData` skips `messages_fts_*` shadow tables. A query under three characters has no trigram and runs as a bounded `LIKE` (newest rows first, stops at the limit). The index holds every message; visibility is decided at query time: unarchived, `user_visible` conversations, no `bot_result`, `scheduled_task` (including legacy ones), `internal`, `progress`, `notice` or `message_ref` rows. Hits are newest first; `match_start`/`match_len` are UTF-16 offsets into `snippet`. The index is about three times the message text on disk. Tests: `search_test.go`, `npm --prefix ui run test:search-palette`, catalog section "Sidebar" states `search-*`.

# Asking a human (one rendezvous)

Every Bot-to-human question goes through the durable questions rendezvous in
`internal/app/questions.go`: it suspends the run (`runtime.SuspendForUserInput`
plus `run_input_waits`), survives restart, expires (30 min by default) and is
shown by `ui/src/QuestionCard.tsx`. Model tools: `ask_user_question`,
`request_approval`, `ask_user_form` (webpage fields; password fields are sealed
into the vault and return an origin-bound `secret_ref`) and `request_secret_input`
(one secret with no website: a thin front that stores a one-password-field form
question; its `secret_ref` is bound to the run, Bot and conversation, lives 15
minutes, is consumed by `use_secret_input` for env/ssh/shell_exec only and is never typed into a page). Do not add a second mechanism:
no polling loop in a tool, no separate HTTP route, no callback hook. Passwords
are written only to the vault (`AnswerUserForm`), never to SQL, events or results.
All of these, and the MCP approval gate, refuse a conversation that is not user-visible (`requireHumanPresent`,
outcome `conversation_not_user_visible`); a hidden Bot-to-Bot run reaches a human only
through its reply, which returns to the assigning Bot or conversation. Mail drafts
(`prepare_email`) are still a separate card path.

A person's own message supersedes an open card: `addUserRunsSteering` (and `steerTriagedMessage`) call `supersedeRunQuestionsTx` (`steer.go`) in the same
transaction that queues the message for the parked or working run. Every pending card of that run (approval, MCP call approval, question, form; not takeover or
connection) goes to `cancelled` with `answered_by='superseded'` (card field `superseded`), through the same single `UPDATE ... WHERE status='pending'` as the other
cancel path, so an Approve that committed first stands and a superseded card can never be approved. The run resumes at once and reads `supersededResult`
(`executed:false`), then the message at its next boundary. Schedule runs and runs under a schedule are left alone; other Bots' messages never come through this path.

Bot secrets (`internal/app/bot_secrets.go`, design `docs/design/bot-secrets.md`): the person, never the Bot, may tick "Save for this Bot" on a
`request_secret_input` card (`save_as` in the answer, `AnswerUserFormSaving`); the record is vault kind `bot_env` scoped by `BotID`, never listed
under Settings credentials. A Bot uses one only by naming it in `computer_shell` `secrets`: the host adds it to that one command's environment at
dispatch (guest `shell.exec` `env`), masks it in the command's output and in later `computer_*` results of the run, and a Bot-scoped secret beats a
global one of the same name. No Bot tool reads, lists values of, or deletes a secret; management is owner-only `/api/bots/{id}/secrets`.

Two Bot-initiated handover cards ride the same rendezvous (`internal/app/handover.go`, UI `ui/src/HandoverCards.tsx`,
`ui/src/TakeoverDialog.tsx`); they add question types `takeover` and `connection` and one stored column (`questions.handover_target`, added by
`ensureColumn`). Their answer is one enumerated word (takeover: `done`/`cannot`; connection: `connected`/`failed`/`declined`) and the model result
(`handoverResult`) is a status word plus a fixed sentence: nothing the person types, copies or sees on the remote screen is part of an answer,
event, result or table (the keystroke/clipboard path stays browser -> `/api/computers/firecracker/actions` -> guest). `request_takeover` (needs the
shared computer; site is stored as an origin only; window <= 14 min because the guest collects an idle desktop after 15) opens a modal around
`RemoteDesktopControl`, which acquires with `handover_question`: that hold is bound to the open card, is never yielded by the 15 s idle release
(`desktop.control.renew`) and ends on the next heartbeat or on answer/cancel/expiry/run start; the run's own desktop tabs are kept while it is parked
on the card. `request_connection` runs the Settings connect flow for this client (native app, https popup, or the shared computer on plain http,
via `mcpOAuthRoute`; a loopback-only service, below, signs in by paste-back instead); `connected` is accepted only if the server sees the token (`connection_not_ready` otherwise); a blocked route reports
`failed`, a retryable error keeps the card open. Both cards are refused in hidden conversations (`requireHumanPresent`) and, like
`ask_user_question`, park and expire in scheduled runs. `manage_extensions oauth_required` points at `request_connection` only in
user-visible conversations.

# Tasks and waits

A delegation is a task and a wait (decision 0059, `internal/app/tasks*.go`, `waits.go`, `bot_inbox.go`, `wait_sweeper.go`, `task_*.go`). A task is a `work_items` row
with task columns (`assigner_kind/assigner_bot_id`, `root_task_id/parent_task_id`, `origin_run_id/assignee_run_id`, `spec_version`, result fields, `closed_at`);
statuses add `input_required` and `failed`. `recordTaskForChildTx` makes it inside the transaction that creates the child run (`AddHandoff`,
`AddForwardHandoff`, `AddBotMessage(s)`), with the `task_result` wait the assigner holds; the existing return run still delivers the result, so that wait
settles in silence (`delivery='legacy'`). Run hooks keep the task true: `SetRunStatus` (start, failed, cancelled), `finishRunOpts` (result, `done`/`review`/`blocked`),
restart recovery, and the sweeper's `reconcileTaskRuns` for paths that miss them. A retry run takes over the task; a run a newer message took over passes it on.
`task_checklist`: the holder sets an item's status and reason (every ended item has a reason). Editing (owner 2026-10-24, `task_edit.go`): the holder and the giver may both change the request (`spec_version` +1), add, remove, rewrite (`rewrite_items`) and reorder (`order`) items, change dependencies, and merge (`absorb_task_id`); only the giver answers, accepts or cancels, only the holder reports status and item results. Every such edit needs `reason` (`edit_reason_required`), is logged in `task_edits` (task, version, actor, role, kinds, reason, detail; `task_revisions` gains `reason`) and is told to the other side through a non-waking inbox row (a changed request from the giver still wakes the holder; the giver gets the holder's edits, none when the person gave the task). A blocked item ended as skipped also tells the giver (`blocked_to_skipped`). Idle-budget anti-gaming: progress marks are keyed by `task_checklist.mark`; an item the holder adds has a `h:` mark and never counts as progress, a rewrite keeps the item's mark, a giver-added item counts once. Merge (`mergeTasksTx`): same tree only (`merge_other_tree`), refuses self, the tree root and an ancestor; checklists join (24 max), the progress marks of absorbed items carry over, tasks that depended on the absorbed task depend on the survivor, children and pending `task_result` waits move, the absorbed task closes as `cancelled` with `work_items.merged_into` and a pointer in `result_summary`, everyone it touches is told.
`say(outcome=done)` with an `open` item goes back once, in the run's one send-back shared with the `pending` check (`state.pendingCheck`).

`waits` is the one table for waiting: kinds `bot_post`, `task_result`, `human_answer` (a mirror of a question card; the card keeps its own resume), `command_exit` (decision 0061), `timer`; groups `any`/`all`; a group settles once (`settleGroupTx`) into one `bot_inbox` row. `recordWaitTx` runs the cycle check in the same
short transaction (walk <= 64 steps, code `wait_cycle`, a graph too large to walk is refused) and the limits (16 open per Bot, `wait_chain_limit` after 24 self-wakes in a row).
A timeout is a result: `timed_out` (a timer is `fulfilled`). Per-kind defaults are `waitTimeoutFor` (15 min / 2 h / 30 min). There is no in-memory timer: one sweeper
(`sweepWaits`, 15 s, also at start) ends due waits, reconciles question mirrors, and calls `flushInbox`. Tests call `sweepWaits` directly; do not add `time.AfterFunc`.
`flushInbox` wakes a Bot with a new `group_followup` run whose `run_wakes.source` is `inbox` (the rows are the request, block `[wait result]`); a single `bot_post` wait in a
group keeps the old mention wake (`via='mention'`). A Bot's own run reads unread rows as `[task updates]` (`consumeInboxForRun`, idempotent per run) when it starts, and at each boundary while it runs
(`drainInboxForRun`, decision 0062, section "Per-Bot lanes and queued steering"); a Bot that is not running is woken by a new run. `outcome=pending` is honest only while the run holds a pending wait (`runHasPendingWait`).

Visible group delegation (decision 0065, owner 2026-10-25, `group_visible_delegation.go`): when the conversation is a user-visible group and every recipient is a current member, a `delegate` (or `handoff`/`message` alias) call posts ONE ordinary message (`kind=''`, sender = the giver, `run_id` = the giver's run, `client_message_id` = `delegation:<id>`) with the text `@<name> [@<name>...] <brief>`; the recipients' `group_task` runs live in the group and have that message as `trigger_message_id` (`addHandoff` for one, `AddGroupDelegations` for several; second and dependent tasks post the message through `publishDelegationMessage` and start through the inbox). The task keeps the brief without mentions. `notDelegationSQL` keeps the message out of `hasPostedMessage`, the silent check, run audit and the last-message fallback; `isVisibleDelegation` lets the recipient's `[current handoff task]` block read it (and history skips it); `validateMCPScheduleEdges` accepts it as an assignment anchor. DM, other-group and non-member recipients and hidden-trace groups keep the notice/forward/hidden-trace paths; the notice rendering stays for old data and those paths.

Tools: `delegate` (one member = handoff path, several = message path; `title`, `checklist`), `wait_for` (receipt at once), `cancel_wait`, `task_update`, `task_ask`, `say` with
`task_id`. `handoff` and `message` are deferred aliases for one version. `cancel_wait`, `task_update`, `task_ask` are on demand (`onDemandTools`): the `[waiting on]`,
`[task record]` and question texts say how to load them. Tool and block texts are English principles in Simplified Technical English with no examples.
A person's message to a member that holds a task bumps `spec_version` and stores a `task_update` row for both sides (`noteUserMessageForTasks`); a message queued as steering (ingress, triage steer, failed-triage fallback) does the same for the task the target run holds, whoever gave it, in the transaction of the delivery (`noteUserMessageForBotTasksTx`), and the run's `run_spec_version` follows when it reads the message (`runReadsCurrentVersionTx`), so `result_based_on_version` is true; results carry
`result_based_on_version`. Context blocks `[waiting on]` (<= 1600 runes), `[task record]`, `[task updates]`, `[wait result]` each have a row in `contextMarkerKinds` and a
`chat:runContext.kind.*` string in 7 locales. Stop (`CancelRunTree`), Bot delete (inside `deleteWorkspaceTargetWith`) and group member removal (`UpdateGroup`) end tasks,
waits and the runs below them by `parent_task_id`/`origin_run_id`/`assignee_run_id`; `GET /api/bots/{id}/task-impact?group_id=` feeds the confirmation count.
Retention (`task_retention_days`, default 30, 0 = keep) clears the request text, checklist and revisions of finished delegated tasks, ended waits and read inbox rows; it never
touches messages, attachments or runs, so the files a failed run kept (decision 0038) stay. Messages a run sends after it registered a wait count against their own
allowance of three (`chatSegmentCountTx`, decision 0050 unchanged before that). The new tables are not exported (`portable*`).

Claim and pass (decision 0060 part C, `internal/app/task_claim.go`). Group triage (`AddHandoff` with sender `system`) makes a task in the same transaction as the answering run: holder = the chosen member, giver = the person (`assigner_kind='user'`, no wait, no inbox), `assignee_run_id` = that run, so a one-turn answer closes it as `done` with no tool call. `claim_task` (holder only, idempotent; writes `task_claims`, moves `todo` to `in_progress`, posts nothing) and `pass_task` (holder only, reason required, target an active member of the same group, at most 4 passes per task via `task_passes`; one transaction: new holder, status `todo`, claim cleared, `assignee_run_id` = a new queued `group_chat` run for the new holder, a non-waking inbox row with the reason; giver, waits, tree and checklist unchanged) are group-only on-demand tools (`onDemandTools`). `WorkItem.claimed_at` is read from `task_claims` in `decorateTaskTx`. The group prompt carries `groupTriageGuidance` (English, STE, principles only); the triage prompt lists up to 12 unfinished group tasks with holders (`openTasksForTriage`). `workItemEventTx` also sends the `work_item` event to `work_conversation_id`, so a task delegated to a Bot's chat draws its card there. `GET /api/conversations/{id}/task-cards` feeds cards and the member list. Hidden small talk (owner 2026-10-24): triage's task is created with `work_items.hidden=1` (data kept). A `hidden=1` task sends no `work_item` event, and `task-cards` and `ListWorkItems` (TeamBoard, WorkPanel, `list_work_items`) leave it out. `promoteTaskVisibleTx` is the one place that shows a task (`hidden=0`, then the card event): a checklist item is added (`addChecklistItemsAsTx`), the holder's run delegates or registers any wait (`recordWaitTx` via `promoteRunTasksTx`), a claim or pass, the first round ends with the task open (`taskFinishedOneTx`), or a second run works on it (retry, return run, steered successor, `say(task_id)` from another run). A one-turn answer that closes the task stays hidden.

Dependencies, giver inbox, stall and tree budget (decision 0064; `task_deps.go`, `task_stall.go`, `task_tree_budget.go`). `delegate` takes `depends_on[]` (task ids of one tree, kept in `work_items.depends_on`): a task with an open dependency is `blocked` with no run (`AddDependentTasks`); `settleClosedTaskTx` is the one place that reacts when a task closes: `done` unlocks each dependent whose dependencies are all done (`unlockTaskTx`: status `todo` plus one waking `task_update` row, same transaction), `failed`/`cancelled` tells the giver and leaves the dependent blocked. Only a run woken from the unlock row (`wakeBotFromInbox` calls `bindUnlockedTasksTx`, one unlocked task per run via `onlyFirstUnlockRow`) becomes the task's `assignee_run_id`; boundary and context reads skip unlock rows (`unlockRowSQL`). `dependencyCycleTx` walks the stored lists (<= 64 steps, `dependency_cycle`, an unwalkable graph is refused); `task_update` takes `add_depends_on`/`remove_depends_on` (either side, with a reason) for a blocked task that has not started. A second single-recipient `delegate` in one run, and any `delegate` with `depends_on`, does not use the run's one direct hand-over: the task starts through the inbox, so independent parts run in parallel. Every visible message a holder posts for a task another member gave (`routeHolderMessageTx`, called where `publishSay` and `publishAssistantPartsOpts` store a `segment`) is a `progress` inbox row of the giver with `wakes=0`; asks, results and stall reports wake; the holder's result marks that run's progress rows read (`supersedeProgressTx`). Stall: each round that ends with the task open compares `progressSigTx` (checklist states plus blocked/input_required) with `work_items.stall_sig`; `stall_count` reaching `task_stall_rounds` (default 3) reports once to the root member (`reportStallTx`); a changed signature resets it. Tree budget (owner amendment 2026-10-24: it guards against spinning, not real work): `task_tree_budget` per root task (or `run:<root run>` outside any task) counts Bot-to-Bot messages WITHOUT progress; `chargeTreeTx` counts hand-overs, mention wakes, waits on posts/results and ask/update messages (holder progress is not charged; the giver's answer to a question always passes). Progress anywhere in the tree resets the count and `reported` to 0 (`resetTreeIdleTx`): a checklist item that ends in `task_update`, a task of the tree that closes done (`settleClosedTaskTx`), a result submitted (`taskFinishedOneTx`, status done or review). Repeatable progress counts once per mark in `task_tree_progress` (`progressOnceTx`): an item the first time it ends, a result the first time per `spec_version`; reopening/re-ending or resubmitting does not reset. `treeKeyForRunTx` is the one resolver of a run's tree (inherited `run_tree.tree_key` from the waking inbox rows, assignee, origin) and every inbox row stores `tree_key`; parts handed out through the inbox share one wait group (the giver hears once); `task_tree_idle_message_limit` (default 30, 10-500; the old `task_tree_message_limit` value is migrated by `migrateAutomationSettings`) refuses new member-to-member dispatch with `task_message_limit` until progress resets it, and the count reaching the limit wakes the root member once per idle stretch with a private inbox row carrying a system-data block (`reportTreeLimitTx`; `afterTreeLimit` files it for a refused, rolled-back transaction). Nothing is posted to the chat: the `system` notice `tree_limit` no longer exists; the person hears only what the root Bot chooses to say. It replaced `maxHandoffRounds` and `maxMentionWakesPerLineage`; the `wake at most 3` fan-out check stays. Both numbers are settings read through `autoIntTx` inside store transactions.

Divide and conquer, line A (owner 2026-11-01, `internal/app/task_contract.go`, `task_deps.go`). No new tool and no Skill: `delegate` carries the contract of a part. A1: `delegate` takes `result_format` (<= 400 runes), `limits` (<= 400 runes) and `deadline_seconds` (60 s to 7 days; codes `result_format_too_long`, `limits_too_long`, `deadline_range`). They are columns of `work_items` (`result_format`, `limits`, `deadline_seconds`, `deadline_at`, plus `progress_line`, `progress_at`; `ensureColumn` in `tasks_schema.go`, read into `WorkItem` by `decorateTaskTx`, not part of `workItemAllColumns`). The deadline runs from the start of the holder's run, not from when the task was made, so the queue of a busy member costs nothing: `deadline_seconds` is stored with the contract, and `startTaskClockTx` (called by `taskRunStartedTx`, which both `claimRun` and `SetRunStatus` reach) sets `deadline_at` and moves the giver's pending `task_result` wait to that time (a timeout is a result, the task itself stays open). The receipt has no `deadline_at` until the run starts; the unlock wake request says "Deadline: N minutes, counted from the start of your run." A task with no `deadline_seconds` keeps the old two-hour task wait (`waitTimeoutFor`). The holder reads `Result format:`, `Limits:`, `Deadline: N minutes left` in `[current handoff task]`, `[task record]` and the unlock wake request (`taskContractLines`). The receipt (`delegatedTaskReceipt`) has `deadline_at` and `runs: serial` for a part the Bot gave to itself. Self-delegation (decision 1) is allowed and always starts through the inbox (`AddTasks`, never `execHandoff`): the part waits for the giver's own lane, so it runs after the giving run. `AddTasks` is the one place that makes the tasks of a delegation call in one transaction (`AddDependentTasks[With]` wrap it). A2 (`task_parts.go`, `task_fanout.go`): `delegate` takes `parts[]` (each `bot_id`, `task`, `title`, `checklist`, `depends_on`, `attachment_ids`, `result_format`, `deadline_seconds`, `limits`), exclusive with the flat fields (`parts_exclusive`). One call = one transaction (`AddTasks`) that makes the N tasks, posts ONE group message `@name title; @name title` (`insertPartsMessageTx`, `client_message_id` `delegation:<id>`, triggers nothing: the parts start through the inbox) and puts the parts in one wait group (mode `all`); the receipt names `group_id`, so the giver ends its turn `pending` and wakes when every part ended or a deadline passed (the group settles once). A refusal leaves nothing behind. Limits are settings (Settings > Automation, group reliability, 7 locales, `go generate ./internal/app` for the registry and manual): `task_fanout_width` (default 4: parts per call; open tasks of one tree <= 2x, code `task_fanout_width`), `task_fanout_depth` (default 2: levels below the root task, from the `parent_task_id` chain of the task the delegating run holds; the root is 0, so a holder at depth 2 is refused, code `task_fanout_depth`), `task_part_deadline_minutes` (default 30; only a `parts[]` entry with no `deadline_seconds` takes it, a single flat `delegate` keeps its two-hour wait) and `task_part_deadline_scheduled_minutes` (default 60, when the run or an ancestor run is a `schedule` run, `runUnattended`). `delegateParts` applies the default deadline. `checkFanoutTx` runs inside the insert transaction of `addTasks` (so two members cannot both pass the open-task limit) and, for the hand-over path, in `delegateTool` before `AddHandoff`. `addTasks` also runs the hand-over rules for every part of a group (`checkPartRecipientTx`: `coAddressedRootTx` under structured output, and `delegationConflictTx`, whose steer outcome is refused too because a part cannot steer a run); a part for the giver itself is exempt. A refusal leaves nothing. A3 (`task_plan.go`, `members_context.go`): the task card of a lead is its plan. Every task a run gives (`addTasks`, `shapeDelegatedTasks`) adds an item `mark='p:<child task id>'` to the checklist of the task the run holds (`parent_task_id`; none when the giver holds no task), text `title · holder name`; the item makes the card visible. A run that holds no task and gives its first part (the Bot a person addressed) gets a root task first (`ensureLeadTaskTx`, called by `addTasks`, so `parts[]`, and the dependent tasks; the flat single hand-over path `recordTaskForChildTx` is not changed: tree budget and stall tests key on its first task as root): held by the run's Bot, given by the person (`assigner_kind user`), in the run's conversation, titled from the run's trigger message; it is the parent of the parts, and the run's later calls join it (the ancestor walk finds it). It closes by the ordinary settle rules, with the lead's answer (done; blocked when a part is still open, since nobody reviews it), and `closeIdleLeadRoots` closes one nothing works on any more after 10 minutes; it is marked `source='lead_plan'` and stores `plan_message_id`, the message where the parts were given, which the plan card anchors on. # Per-Bot lanes and queued steering

One Bot runs one run at a time, across every conversation it is in; different Bots run in parallel (decision 0062, `internal/app/bot_lanes.go`, `steer.go`). The conversation worker
(`runConversationWorker`) still looks at one conversation's queue, but `pickRunnable` returns the first run whose Bot has a free lane and `launchRun` starts it in its own goroutine
under that lane (`Server.lanes`: Bot id to run id in memory, plus a database recheck of `status='running'` for the same Bot; a claimed approval settlement does not count).
`triage` runs take no lane. A freed lane wakes every worker; a worker with something waiting on a lane or an order also rechecks every second. Heads of different conversations compete
by `laneRank`: same task tree as the run that just left the lane > a person's message > a delegation > a schedule (approval settlement first); inside one conversation the older order
stays. `runOrderBlocked` keeps two orders the serial worker gave for free: a run waits while the run that created it is running or queued, and a Bot addressed with others by one
message waits for the ones addressed before it. Tests that call `execute` directly bypass lanes: do not add code that relies on `launchRun` for correctness of one run.

A person's message to a Bot that is working is not a new run and cancels nothing. `addUserRunsSteering` (the ingress transaction) asks `steerTargetTx` for the Bot's running run in this
conversation (or in work whose origin is this conversation), or its run parked on a question card; one that already recorded its `say(answer)`, one that yields to a steering successor, an
approval settlement and a scheduled run are not targets (a message during a scheduled run starts a run of its own and the scheduled run yields to it, as before). The message is stored as always; a `bot_inbox` row (`kind=user_message`, `parent_run`, `anchor`=message id) says where it went, and the response carries
`queued`. `Message.delivery` is `queued` for unread rows (history never lists `read`); reading emits the stream event `inbox {message_id, run_id, state}`. The run reads at the boundary before each
model request: `Request.DrainInbox` (`agent.AgentConfig.DrainInbox`) calls `drainInboxForRun` (one transaction: marks the rows read, `drained=1`, emits the event), the agent appends one user
turn (`renderInjection`: `[new message from the person]` with the principle, or `[events from the task system]`), checkpoints it and refills the run's time, call, step and cost budget once
(`Continuation.BudgetCallsBase/StepBase/CostBase`). Every read counts toward `maxInjectionsPerRun` (5), and none happens past `injectContextShare` (60%) of the context window or within `minTurnsForReading` (100) of the assistant-turn limit (a refill is also cut to fit under it, `refilledStepLimit`); only a person's message refills the budget (`DrainInbox` returns `refill`). Past those limits the next unread person message
closes the run through `closeRunForContinuation` (a continuation run plus the old steering edge, then `steeringBoundary` yields). Other inbox rows of the Bot in this conversation (settled waits,
a member's question, task updates; not `via=mention`, not rows waiting for a still-active run) are read the same way. Messages still unread when a run ends become one continuation run in the
same transaction (`continueUnreadInboxTx`, from `finishRunOpts`, `SetRunStatus`, recovery and `MarkRunSteered`); Stop all drops them. A read that a restart lost before its checkpoint is given
back (`returnUndeliveredDrainsTx`, in `claimRun`). While a question card is open the card stays and the message waits for the run that resumes (`supersedeInputWaitsTx` skips a parked run with an
unread message). The `run_steering` edge and `steeringBoundary` remain for delegation, mention wakes and the cap; a person's message makes no edge any more. Delegation returns are still queued
return runs (`group_followup`), not inbox reads.

Two stop levels: `POST /api/runs/{id}/interrupt-step` cancels only the tool call in flight (`runtime.Request.BeginStep`, per-call context, typed outcome `step_interrupted`; 409 `no_step_in_flight`
when only the model is running) and the run goes on; `POST /api/runs/{id}/cancel` is Stop all (`CancelRunTree`, tasks and waits too). The composer is always enabled; its Stop button is in the entry (Stop all by itself when the menu chunk is not loaded) and opens the lazy two-item
`ComposerStopMenu` (`ui/src/ComposerStopMenu.tsx`; the step item only for a running run with a tool call in flight); the queued/read note is `DeliveryNote`, applied from the `inbox` event by `applyInbox` (`ui/src/messageDelivery.ts`).

# Task continuity

A newer person message may still take a Bot away from running work (a scheduled run yields to it), but the work is not lost (`internal/app/task_continuity.go`). A run is evidence, a task is what was
asked: the unfinished work is a `work_items` row of the Bot in that conversation, paused as `status='todo'` with `interrupted_at` set (columns added by `ensureColumn`: `source` `user_request|schedule_occurrence`,
`source_run_id`, `schedule_id`, `interrupted_at`, `interrupt_reason`, `resume_count`, `resume_state`; a paused task is `hidden=0` and has no `assignee_run_id` until it resumes). Hooks, all inside the transaction that ends the run:
`MarkRunSteered` calls `pauseForPersonSteerTx` (only when every run the old one yields to is a person-message run of the same Bot and not a continuation of the messages it left unread; a delegation, mention
wake or reading-cap hand-over is not an interruption) and then `resumePausedTasksTx`; `finishRunOpts` and `SetRunStatus` (done, failed) call `resumePausedTasksTx` too. `resume_state` (<= 4 KB JSON: goal, the run's
progress messages, the last 16 tool calls with bounded args and results, the person's unread message) is written by the harness, because a cancelled run has no turn left. `resumePausedTasksTx` starts the oldest
paused task as a queued run when the Bot has no other queued or running run and no unread person message in the conversation (a person's message always goes first), at most `taskAutoResumeLimit` (2) times per task
(`resume_count`; the person's Resume button, `POST /api/work-items/{id}/resume`, is not counted). The resume run is a child of the interrupted run with the same kind (a scheduled occurrence stays `schedule`, so
`scheduleFamilyOutcome` and `completeOneTimeScheduleTx` treat the cancelled ancestor as superseded by its descendant), `resume_notice='task'` (the chat notice "Resuming: title", `HandoffNotice.task_title`) and, for a person's
request, the newest person message as trigger so its history shows what came in between. It reads the `[unfinished task]` block (`taskResumeContext`, kind `unfinished_task`). Early stop: `finishRunOpts` calls `captureEarlyStopTx` after the task hooks; a person's request that ends with `say` outcome `pending` and no pending wait is paused
(`interrupt_reason=early_stop`, then resumed like any paused task), one that ends `blocked` becomes a `blocked` task that waits for the person (no run). Every run of the Bot (not triage) reads the `[unfinished tasks]` list block
(`unfinishedTasksContext`, <= 8 paused or blocked entries, kind `unfinished_tasks`): a person's "continue" refers to it, and `update_work_item(status=in_progress)` on a paused entry binds it to the running run
(`bindPausedTask`) and returns its record, so it is not resumed a second time. A task of a schedule that has claimed a newer
occurrence is cancelled (`result_summary=superseded_by_next_occurrence`); Stop all (`CancelRunTree`) cancels the Bot's paused tasks in that conversation. UI: `Run.paused` (title, set by `decoratePausedRuns` and the steered
run event) makes the stopped line "Paused: title"; the paused `TaskCard` (lazy) has Resume and Drop (`PATCH` status `cancelled`). Entry JS has about 1 byte of budget headroom: keep further changes in lazy chunks.
Steering keeps the task: the boundary read says a message that arrives during work is added to the request and the final answer covers the original request too. `say` offers `covers_original` (column `run_say_answers.covers_original`, persons' runs only, so their say is no longer strict). A run that read a person message (`bot_inbox` drained) and ends `done` without `covers_original`, no pending wait, is paused by `steeredAnswerLeavesOriginalTx` in `finishRunOpts` (`interrupt_reason=steered`, uncapped) and resumed like any paused task. Test: `steering_keeps_task_test.go`.
Tests: `task_continuity_test.go` (the owner's sequence), `task_continuity_limits_test.go`, `lane_schedule_concurrency_test.go` (a scheduled occurrence queues behind a running person's run).

# Security gates

`manage_extensions` changes (MCP create/update/delete/test, Skill `skill_publish_version`) execute only after a person's
approval of the exact payload (`internal/app/extension_gate.go`: request_approval target = digest token, one use) and are refused in unattended
runs. A Bot installing a skill for itself (`skill_install`) or turning a library skill on or off for itself (`skill_enable`/`skill_disable`) touches no
other Bot and needs no approval (decision 0058); install is still refused when no person can see the run, enable and disable are allowed there. The
approval card carries server-built `approval.facts` (kind, name, address with masked query, transport, tool lists, header names, skill manifest
summary, and for a published version the new version number, files added/removed/changed against the current files and how many Bots follow it)
rendered above the Bot's own wording; the Bot cannot set them and a token the server has not seen in the run gets no card. `skillPublishGuard` refuses,
before any card, a publish by a Bot that did not install the skill, for a missing skill, an invalid file set or files equal to the current version.
Bot-created MCP servers are refused for loopback/private/link-local/CGNAT/metadata hosts at create time (fail closed on DNS errors, odd numeric
forms, IPv6/mapped/NAT64/6to4) and again at every connection: `bot_managed` servers dial through `extensions.GuardedTransport` (dial-time `Control`
hook, no env proxy, redirects never followed). The owner's allow path is Settings: a server saved there is not `bot_managed`. A spent approval is
returned only when the guarded call fails with certainty before any effect (`not_executed`); otherwise it stays spent. Click approvals
(`claimApproval`) match the label in one normal form (`approvalLabelText`, also what the refusal shows) and are consumed once
(`click_approval_claims`). Login limits are per peer address (IPv6 /64) and per account identifier; a peer that earlier proved the password skips
the per-identifier bucket (`owner_auth_known_sources`) so strangers cannot lock the real user out; password changes use their own `pwchange`
bucket namespace; there is no global bucket.
MCP write-tier calls can be allowed for good with "Always allow" (`internal/app/mcp_standing_allowance.go`, table `mcp_standing_allowances`, created by
`migrateStandingAllowances`: `CREATE ... IF NOT EXISTS` + `ensureColumn`). A grant is (account, Bot, MCP server, tool), independent of the payload, and
binds to the server's config fingerprint (name, address, transport, headers), a digest of its credential target, and the tool definition digest
(`MCPToolTierView.Digest`: name, description, schema, annotations): a changed definition or server voids it (Settings shows `tool_changed` /
`server_changed` / `tier_changed`; the next "Always allow" supersedes it). A server change is sticky: `server_changed_at` is set the first time a
different identity is seen (configuration writer hook `Config.ServerIdentityChanged`, any call, the Settings list), so setting an address back does not
revive it; an out-of-process file edit that is changed and reverted between two looks is the one gap. It is created only by the owner question route from a
card the gate marked `standing_eligible` (write tier, conversation a person can see), never for `high_risk`/read-only tools, never from model input
(`approval.standing` is reserved like `remember`); the archived-Bot check is part of the INSERT. Setting a tool to "Always ask me" revokes its grants
(`revoked_by=tier_raised`). It decides when no person attends too (schedules, Bot turns, inbound content) and says so in the card hint and Settings, but
never in a conversation no person can see (`matchStandingAllowance` needs `UserVisible`, and a live grant in a hidden conversation refuses with
`conversation_not_user_visible` even in an unattended run). In AutoReview "auto" mode the reviewer still runs: the grant replaces only the "a person
decides" verdict (`finishMCPReview`); a deny still blocks. The decision is a card answered by actor `standing-allowance`, re-validated at claim time
(`standingClaimValid`), so Revoke (Settings > Permissions, `/api/standing-allowances`) bites an in-progress run at its next call (attended: the
card returns to a person; unattended: it is closed and the call refused `mcp_needs_human_unattended`). Each use bumps `use_count`/`last_used_at` and
writes `mcp_standing_allowance_uses` (null `call_id` when the runtime gave none) inside the claim transaction, and links the tool activity
(`ToolActivity.allowed_by`). Archiving/deleting the Bot or the server (`deleteMCPServer`: use it, not `extensions.DeleteMCP`) revokes the grants
(`revoked_by` `bot_archived` | `bot_deleted` | `server_removed`) and keeps the rows and uses.
Local MCP Runner (decision 0071): in multi-account self-host it is the `runner` container (profile `runner`), not a process in the guest. Each account has a namespace
`/a/<account id>`, a token derived from the master key (`mcprunner.AccountToken`), a uid and private directories; `localRunnerConfig` uses it when the account has no computer or its
guest Runner state has been copied and verified (`local_runner_container.go`, state file `local-runner.json`). Never route a request to another account's namespace, never give a
workspace the master key, and keep `internal/mcprunner/hub_test.go` cross-account refusals passing. Root-side file work inside an account (below `plugins/<id>` or `tmp/`, which the account's uid owns) must go through `os.Root` (`confined.go`), never `os.ReadFile`/`os.RemoveAll`/path `chown` on a path the account can swap; the directory owner, not `uids.json`, is the authority for an account's uid. The guest Runner code stays only as the source of that copy.
Runner sandbox (`sandbox.go`, `sandbox_linux.go`, `seccomp.go`, `diskquota.go`): every child of an account starts through `confine()`, which makes the Runner binary a root launcher that joins the account's cgroup (memory+pids) and network namespace (`unshare --net` holder, veth to the container, forward to the egress interface only, DNS forwarder on 127.0.0.11 inside the namespace), unshares IPC, then drops every capability, sets no_new_privs, becomes the uid and installs a seccomp filter before exec. Never start a plugin or installer with `Credential` directly when a sandbox is configured, and never add a capability to the `runner` service without writing why in `compose.yaml`. Account cgroups need the container's own cgroup view writable: compose gives the Runner `cgroup: private` and the `tofi-runner` AppArmor profile (`deploy/self-host/runner.apparmor.template`, docker-default plus one remount rule; loaded by `prepare_runner_sandbox` in `tofi_host.py` before the Runner starts, which also sets `TOFI_RUNNER_CGROUPS=required`). The Runner never remounts in the host's cgroup namespace (`checkCgroupRemount`). Disk is a measured quota per account (`Options.Admit`).
Community connections (decision 0047): TOFI curates official connectors only; a community MCP is installed by the person under Settings > Connections > Add connection > Custom > Local package
(npm or PyPI, pinned version, optional npm `sha512-` digest verified after install). Its secrets are 0600 files in the Runner, never in a response, status or manifest.
`attachLocalMCP` writes `provenance` (origin `community`, kind, package, version) from the Runner's status only; it is part of the configuration fingerprint, so a
different package or version voids standing allowances. For a community server the provider's `readOnlyHint` is shown but not obeyed (`communityServer` in
`resolveMCPToolTier`): its tools are reviewed as writes until the owner marks them read-only. Installed Skills with scripts are copied to the Bot's computer on
`read_skill` like built-in ones, so prefer MCP for anything holding a credential. Pins and recipes live in `integrations/`.
Session cookies are Secure when `TOFI_PUBLIC_ORIGIN` is https; Caddy sends HSTS. Known open: `computer_shell` shares a uid and loopback with the
shared Chrome DevTools port.

# Web search and fetch

`web_search` and `web_fetch` are server-run tools (decision 0068) for runs whose model has no native search: an Anthropic model with the "Web search" automation switch on gets the provider's own tools and neither of these registers (`webNativeWins`, `web_search.go`). `internal/webtools` holds the providers (Tavily, Brave, SearXNG, the built-in fetch, Firecrawl, Bright Data) and the two chains; `internal/app/web_tools.go` holds the order (one stored `automation_settings` value, key `web_tools`: orders, switches, SearXNG address; D15), the keys, tool registration and the Settings API (`/api/web-tools`). A chain moves on by stable `webtools.Code` only (`auth_failed`, `quota_exceeded`, `blocked`, `empty_content`, `needs_javascript`, `network`, `not_configured`, `unsupported_content`); `target_refused`, `bad_request` and `not_found` end it, so a private address is never handed to a third-party fetcher or the Bot computer. Never put a vendor's message text in an error, log or response. Keys are vault records of kind `web_provider` (id `webtool:<provider>`, excluded from `/api/secrets` like `modelProviderKind`; Bright Data stores `key\x00zone`); the vault record's `Error` holds only a code. `web_search` is registered only when a non-native source is usable (never pretend to search); `web_fetch` always has the built-in fetch. The built-in fetch uses `extensions.GuardedTransport` (dial-time address control, no env proxy; `BlockedAddr` also refuses the host's own interface addresses and the `TOFI_PUBLIC_ORIGIN` host, refreshed each minute), `ValidateTarget` before every hop (`CheckRedirect`, max 5), ports 80/443/8080/8443 only, 20 s, 2 MiB, text and HTML only; `ParseHTML` has node, output and context budgets (keep every loop in it linear). The Bot computer fetch is not behind the dial guard: `webtools.CheckResolved` re-resolves the host before navigating and refuses any blocked answer, which narrows but does not close the DNS-rebinding window and cannot see redirects the browser follows. Paid sources have a rolling 24 h cap each (default 300 searches / 300 fetches, table `web_tool_calls`, adjustable in Settings); at the cap the chain falls to the free sources. Only vendor credential errors become `auth_failed` (Bright Data: 407 only; its 401/403/429 are the target site, so `blocked`). A tool result starts with `{"source":"<id>",…}`; `toolSourceLabel` shows it in Activity. The Bot computer source needs the browser capability (`hasComputerCapability(CapBrowser)`) and `computerAdmission()` (`webComputerExists`/`webComputerOn`). Tool descriptions follow the tools text rules: English, STE, no examples. Settings UI: `ui/src/WebToolsSettings.tsx` (`test:web-tools`). Hosted OpenAI search writes citation spans (U+E200 start, U+E201 end) into output text: `provider.MarkerFilter` drops them in the Responses stream and parse (a span cut across deltas stays hidden; sources come from annotations and search-call sources as before), `stripCiteTags` drops them from any stored text, and `MessageMarkdown` (`hidePrivateSpans`) hides them in messages stored earlier.

# Editing a schedule's timing

`PATCH /api/schedules/{id}` and the Bot tool `update_schedule` accept optional `kind`, `run_at`, `interval_seconds`, `daily_time`, `weekdays`, `timezone`
(`SchedulePatch`, `internal/app/schedule_edit.go`). They go through `planScheduleTiming`, which merges the patch onto the stored schedule and calls the
creation validation and next-time calculation (`validateScheduleSpec`); there is no second calculator. A change recomputes `next_at_utc` from now; a
restated timing changes nothing. Unset fields keep their stored value unless `kind` changes, which starts from the fields the new kind needs
(`daily` <-> `weekly` keep the clock). Failures are `*ScheduleError` with stable codes (`schedule_kind_invalid`, `schedule_timezone_invalid`,
`schedule_run_at_required|invalid|past`, `schedule_interval_invalid`, `schedule_time_invalid`, `schedule_weekdays_invalid`, `schedule_timing_conflict`,
`schedule_timing_locked` = 409); create returns the same codes. It never touches a claimed or running occurrence (runs, `schedule_occurrences`
and the occurrence authorization snapshot are separate rows), leaves a paused schedule paused, and refuses a one-time schedule that was claimed or
completed. `expected_timing` is the opt-in baseline (a mismatch is `edit_conflict`, like `expected`). A timing edit is journaled as a `content_edit`
authorization revision from the same source kinds (form or native chat), so whoever may edit content may edit timing; `verifyMCPScheduleSources` therefore
lets timing differ between revisions (identity and the original anchor must still match) and shows each revision's timing to the reviewer. The UI is
`ScheduleEditor.tsx` using `ScheduleTimingFields.tsx`, the same controls as the create form; `test:schedule-timing` holds its patch building.

# Web timeline performance

The message list is built for cost that does not grow with the conversation. Each row is `MessageRow` (a `memo` component compared by
`rowModelEqual` in `ui/src/timelineRow.ts`); the Workspace derives a plain-data `RowModel` per row and rows call the Workspace only through
the identity-stable `RowHandlers`. Streamed text never goes through Workspace state: `ui/src/draftStream.ts` holds the growing text, `drafts`
changes only in structure (a draft appears, changes owner or sequence, becomes visible, gets a reply marker, goes away), and the one row that
shows a draft follows it with `useLiveDraft`. Do not read `drafts[...].content` in the Workspace for anything but emptiness. A conversation
that opens at its newest message draws `FIRST_PAINT_BLOCKS` blocks first and the rest in the next task (`landing` in `useConversationScroll`
decides; an unread divider, a restored position or a pending task focus draw everything). Settled Markdown is kept as elements (`reuse`).

`test:timeline-rows`, `test:perf-structure`. WebKit has no native scroll anchoring: whatever changes layout above the reader after the position
was set (sender marks, a prepended block) must be followed by `viewport.reposition()` or an anchor.

# Composer resilience (optimistic send, outbox, drafts)

A sent message is on screen at once and never vanishes. Benchmark: iMessage (red "Not Delivered", tap to retry), WhatsApp (resend when the
connection returns), Claude.ai and ChatGPT (the prompt stays, Retry on the failed turn); we follow all three: failed bubble with Retry, Edit and
Delete, one automatic try when the connection is back, the text never lost. `ui/src/outbox.ts` is the outbox: every message the server has not
confirmed is mirrored to localStorage (`tofi:outbox:<origin>:<instance>:<owner>`, same scoping as the drafts). `App.tsx` `send` puts the bubble
(local copy, `message.local`) and the outbox entry in one commit; `deliver` uploads files not yet up (XHR with progress, `api.uploadAttachment`
with a listener), then posts with the same `client_message_id` on every attempt (the server stores it once and replays its answer: no duplicates).
`message.local.state` is `sending | retrying | failed`; `reason` is `offline | network | server | rejected`. The connection coming back (browser `online`
event or the live stream reconnecting) retries each failed message once, in order, labelled "Sending again" (`autoRetry`); a refusal (4xx), a second
failure and a message restored after a reload are never sent by themselves. After a reload the outbox entry comes back as a failed bubble when its
conversation loads (`reconcileOutbox`; an entry the server already holds is dropped). A file not yet uploaded cannot survive a reload (a File is not
storable): Retry is withheld, Edit puts the text in the composer and the file is asked for again (the draft's existing reselect flow). Pictures show
from the device (`attachmentImages.ts` `registerPreview`/`adoptPreview`: one object URL from the local tile to the server's copy) with a progress bar
(`Attachment.pending`); where the server stores files is not touched. Composer drafts moved from sessionStorage to localStorage (read once from
sessionStorage for older drafts), per conversation, per owner. Tests: `test:composer-resilience` (offline -> failed -> reconnect -> sent once,
reload, Delete/Edit, drafts, upload progress), `test:send-receipts`, catalog states `receipts/pending|offline|retrying|failed`.

# Install as an app (PWA, no service worker)

The web app installs to a phone home screen or desktop from `ui/public/manifest.webmanifest` alone (icons in `ui/public/pwa/`,
regenerated from the brand SVG by `ui/scripts/make-pwa-icons.sh`; light/dark `theme-color` pair in `ui/index.html`). There is

`/pwa/*` with `Cache-Control: public, max-age=3600`; UI paths are served before the owner gate, so the sign-in page is installable too

(`ui/src/installApp.ts`, listener started in `main.tsx`) or on iOS Safari (then `InstallSheet` explains Share > Add to Home Screen);
nothing shows when already standalone. Some browsers do not offer install on a self-signed certificate (README, install options).

guest object, check its length, write a temp file and fsync, hash the file and compare, rename, then repoint the row and journal the guest object
in one transaction. The guest object is deleted later by `cleanupDeletedAttachments`, which re-checks the server file against the row's sha256.
A `vm:` file that cannot be reached answers HTTP 409 `file_on_detached_computer` (404 `file_missing_on_computer` when the computer answers and lacks it); the web app shows one sentence for either in the file card and the viewer (`AttachmentNotice`, `attachmentDownload.ts`). The portability import writes its attachment bytes straight to this store (`portability_staging.go`, origin `import`), so it needs no computer. `tofi computer remove --purge` refuses while any `vm:` row
exists unless `--discard-unsaved-files`. Outbox: `/workspace/home/outbox` is copied by `outbox_sync.go` at the end of a run that used the computer
(20 MiB per file, 200 MiB and 8 files per reply, symlinks refused by the guest, nothing deleted on the computer). Design:

# Object storage for files (attachment-object-storage P1)

`internal/filestore` is the only code that reads or writes attachment bytes. `Store` (Put write-once, Open seekable, Stat, Delete, List) has two backends: `Disk` (the flat attachments directory, today's behaviour) and `S3` (minio-go v7, pinned; R2/S3/MinIO/B2 differ only by endpoint, region, path-style; `If-None-Match: *`, MD5, no multipart). Errors are types (`ErrNotFound|ErrUnavailable|ErrDenied|ErrExists`) with no URL, host or bucket in the text; `internal/filestore/fakes3` is the in-process S3 for tests. `filestore.Probe` is the connection test (conditional put, repeat put must be refused, stat, ranged read, unsigned read -> `bucket_is_public`, delete).
- **Where a row lives**: `attachments.disk_name = "obj:<full key>"` plus `attachments.store` (the config generation, `g1`) for a bucket object; anything else is a disk file (or legacy `vm:`). A row is read only from its own place: `openAttachment` never falls back, an `obj:` row never reads disk, a disk row never asks the bucket. The key is stored in full, so later layout or prefix changes never move old files. `Attachment()` returns the `obj:` name as its "path" and `openAttachment` routes on it.
- **Key layout** (`FileStoreKeyPrefix`, `FileBackend.objectKey`): `<prefix>v1/<instance_id>/accounts/<account_id>/<kind>/<attachment_id>`; kind from origin (`attachmentKind`): upload -> `uploads`, published/generated/outbox/mirror -> `artifacts`, trace -> `traces`, import -> `imports`. No user text in a key or in object metadata (`Content-Type` safe MIME, `Content-Disposition: attachment`, `x-amz-meta-sha256`). `instance_id` is the root server's.
- **Writes**: `addAttachmentOpts` spools to `attachments/.spool/<id>` (emptied at start, `clearSpool`), settles size, quota, sniffed type, raster check and sha256 there, then `Put`s; the row is inserted last and a failed insert deletes the object. Quota refusal happens before any bucket request. The portability import goes through the same `Put` (`portableLocation`; the staging journal records `disk_name`/`store` so recovery removes the right object).
- **Named errors, no silent fallback** (`file_store.go`): bucket down on write -> 503 `file_store_unavailable`, credentials/bucket refused -> 503 `file_store_misconfigured`, object gone on read -> 404 `file_missing_in_store`, key outside the account -> 500 `file_store_key_out_of_scope`. A bucket failure never becomes a disk write. Downloads are streamed by the server (no presigned links yet). The web file card shows the three 503/404 codes through `AttachmentNotice`.
- **Configuration** (gateway only; `org_file_store.go`): organization resource `file_store`. Non-secret config (`endpoint, region, bucket, prefix, path_style, gen, kind, delete_grace_days, public_ok`) in `org_resources.config`; Access Key ID and secret sealed together in the org vault (`id\x00secret`), never in a response, log or workspace. A workspace gets a `FileBackend` through `Config.FileStore` (a store handle plus layout, no credential). `PUT` tests the connection first and stores nothing on failure (`endpoint_unreachable, credentials_rejected, bucket_not_found, write_denied, conditional_put_unsupported, range_unsupported, delete_denied, bucket_is_public`); a blank key keeps the stored one only for the same location; changing the location or removing the resource is refused (`file_store_in_use`) while any account has `obj:` rows; `{"kind":"disk"}` sends new files back to disk and keeps the bucket readable. A runtime refusal or outage marks the resource `rejected` (`watchedStore`). The visible settings are the card's fields (destination `kind`, `delete_grace_days`), not the Bot settings registry.
- **Deletion**: deleting a conversation, Bot or unbound file journals `obj:` rows in `deleted_attachment_files` with `delete_after` = now + `delete_grace_days` (default 14); `cleanupDeletedAttachments` (also every 10 minutes from the file store copier, which now always runs) removes the object after the deadline and keeps the journal row when the bucket fails. Disk files are still removed at once. Account deletion has a `files` step before `data` (`deleteAccountFiles`: every object under `.../accounts/<id>/`, no grace, repeatable). A workspace reset deletes its objects first.
- **Hosts and rollback** (`deploy/self-host/tofi_host.py`): `meta.json` of a backup carries `file_store {kind,bucket,gen,objects,bytes}` when rows live in the bucket (`tofi backups` and `tofi restore` say the files are not in the backup); `check_object_rows` makes `tofi update` refuse a release older than `OBJECT_ROWS_MIN_VERSION` while `obj:` rows exist (set that constant to the first release that carries this; today `v0.6.3-rc.9`).
- **Origins**: Bot-generated images and mail-draft attachments are written with origin `generated` and the Bot id (new rows only; older ones stay `upload`).
Not done yet (later phases of `docs/design/attachment-object-storage.md`): moving existing files, orphan sweep, presigned downloads and `direct_downloads`, image previews, per-server config for single-account self-host, upload retention (`upload_retention_days`, `keep_file`).

# Remote backups (backups P1)

Design `docs/design/backups.md` (local; owner answers at its end are final). Phase 1 is the least-logic version: a whole encrypted file per database per snapshot, no chunking or dedupe (that is P3, triggered when one database copy passes 1 GB or a daily backup on the R5C passes 30 minutes).

- **Engine** (`internal/backup`, no HTTP, no accounts): `Repo.Run` captures the root database, then each account database listed in the root *copy* (`accounts WHERE legacy=0 AND deleting=0`; the original owner is `root`, its attachments live under `files/owner/`), one at a time: SQLite online-backup API (`conn.NewBackup`, one step, own read connection) to a staging file under `<data>/tmp/backup`, `quick_check`, `user_version` and row counts (`bots, conversations, messages, attachments`), gzip, AES-256-GCM, one object. Then a tar of the data directory minus `tofi.db*, attachments, accounts, tmp, .spool, backups, backup, host-control.token` (one `files` object), then disk attachments (`store=''`, not `vm:`/`obj:`) that `files/<account>/<attachment_id>` does not list yet. The encrypted manifest is written last and is the commit; then `head.json` with `If-Match`. A database copy over `MaxDBBytes` (1 GB) is `backup_db_too_large`.
- **Bucket layout**: `<prefix>v1/<instance_id>/server/backups/{repo.json, head.json, keys/recovery.json, snapshots/<UTC>-<reason>/{manifest, root/{db,files}, accounts/<id>/{db,files}}, files/<account>/<attachment_id>}`. Only `repo.json` and `head.json` are plaintext; keys hold UUIDs only. Every object is `nonce||AES-256-GCM`, AAD `tofi.backup:1|<repo-relative path>`, so a moved object fails (`backup_object_damaged`).
- **Keys**: a random 32-byte data key per repository, stored in the organization vault as `backup:key` (kind `backup_key`, never in a response) and wrapped under the **Recovery Key** in `keys/recovery.json` with the existing `tofi.encrypted` v1 envelope (`sealExportFile`, PBKDF2 310k). The Recovery Key is `exportPassphrase()` (160 bits, 8 groups), shown once by `POST /api/admin/backups/recovery-key`, never stored; the UI checks the last two groups client-side and then calls `.../confirm`. A wrong key is `backup_recovery_key_wrong`. Rotating rewrites the slot only (`Repo.Rekey`, `filestore.S3.Replace` = `If-Match`).
- **Resource and settings** (`org_backup.go`): organization resource `backup_store` (own bucket, own access key sealed in the org vault, probed with `verifyFileStore`; a bucket that answers without credentials is refused). All settings live in its config JSON and on the Backups card: `remote on|off` (default off; on needs a confirmed key), `schedule daily|6h|hourly|manual` (daily 03:00 server time), `keep_daily/weekly/monthly` 7/4/12, `verify weekly|monthly|manual`, `stale_after_hours` 36. Status is one JSON row in root table `backup_state` (`last_status ok|failed|blocked`, `last_code`, `last_account`, `last_success_at`, `verified_at`, `verify_status`...); `GET /api/admin/backups` returns settings, key fingerprint/confirmed date, status and `stale`. One job at a time (`beginBackupJob`); account create and delete answer 409 `backup_in_progress` while it runs. A process that died mid-run is settled as `backup_interrupted` at start.
- **Failure is visible**: no manifest, no `ok`. Codes: `backup_store_unavailable`, `backup_store_misconfigured` (also marks the resource rejected), `backup_key_missing`, `backup_no_staging_space`, `backup_db_too_large`, `backup_capture_corrupt`, `backup_repo_diverged` (status `blocked`), `backup_interrupted`, `backup_prune_failed`. Upstream text is never returned or logged.
- **Retention** (`backup.Select`, pure): newest per day/ISO week/month for the last N of each, newest three `manual` and `pre-update`, always the newest. `Prune` deletes the manifest first, then the directory, every directory with no manifest, then bucket attachments no kept manifest lists. No bucket lifecycle rules.
- **Lineage**: `head.json{writer_seq,latest}`; the local copy is `<data>/backup/state.json`. A mismatch is `backup_repo_diverged` and backups stop. `restore-remote` takes over (`writer_seq+1`, state written into the restored tree) or makes a copy (`replica`: no `instance.json`, no state, `remote` set off).
- **Drill** (`Repo.Verify`, weekly by default and `POST .../verify`): newest snapshot rebuilt in scratch: every database sha256, `integrity_check`, schema, row counts; vault opened and counted (no values); every disk attachment id must be listed; 20 sampled downloads hashed. Result is `verified_at/verify_status/verify_duration_ms`. It never deletes.
- **Single-account restore** (`account_restore.go`): `GET /api/admin/accounts/{id}/backups`, `POST .../restore {snapshot, confirm_username}`, `POST .../restore/undo`. Fence (`g.restoring`, runtime closed, requests fail until released), fetch into `accounts/.restore-<id>` (the account's current files are reused), swap by two renames keeping `accounts/.before-restore-<id>-<stamp>` 14 days. `recoverRestores` settles a crash between the renames at start. Refused by name: `account_restore_unsupported_legacy`, `backup_instance_mismatch`, `schema_too_new`, `not_found`, `confirmation_mismatch`, `backup_in_progress`. Login, role, group and quota are in the root database and are not touched.
- **Whole-host restore**: `sudo tofi restore --from-remote` (`tofi_host.py` `restore_from_remote`) asks for the bucket and keys, runs `tofi restore-remote` (`internal/app/backup_cli.go`, JSON on stdin so no key is in argv) in the installed App image to list servers and snapshots and to download and check one into a scratch tree, packs that tree as an ordinary local backup (`backup_data(..., data_root=tree)`, current `/etc/tofi`) and hands it to `restore_backup` (pre-restore backup, health check, rollback). A snapshot newer than the installed schema is refused (`backup_schema_too_new`, run `tofi update`).
- **Not done (later phases)**: `tofi update` taking a remote `pre-update` snapshot and `tofi backups` listing remote ones (P2), `/etc/tofi` in the snapshot (P2), chunking/dedupe (P3), `--account` on the CLI, waiting for an account's runs before restore (it cancels them), free-space check before restore, the admin notification event (the Backups card shows status and `stale`), orphan report after restore, a second copy of bucket attachments.

# Provider errors and failed runs

Transient provider failures are retried by code, not by message text: `provider.IsRetryable` (HTTP 429/5xx/529, and the in-stream `response.failed` / `error` codes in `retryableResponseFailure`, which arrive with HTTP 200). `RetryProvider` backs off with jitter, honors `Retry-After` (up to 60 s) and stops at `TotalBudget` (2 minutes); the agent loop retries once output has been delivered. A new provider error code that is transient goes into `retryableResponseFailure`. A provider 400 that no retry can fix and that has a known cause gets a stable code through `provider.RequestRejectionError` (wraps the `APIError`, never retried): `provider_invalid_request_prefill` marks a request that ended with an assistant message. The Anthropic converter closes any assistant-final history with a user turn (`Continue.`), so that code means a defect, not a condition to wait out; `internal/agent/prefill_guard_test.go` builds a request from every loop path and asserts the last turn is a user turn. Do not add assistant prefill to a request. A run that fails after `publish_file` keeps its files: `SetRunStatus(failed)` binds them to an attachments-only assistant message (`keepFailedRunFilesTx`); cancelled and interrupted runs still discard theirs (decision 0038).

Links written as `sandbox:/…` are normalized only on the way out (`Message.MarshalJSON`, `internal/app/sandbox_links.go`); the stored text stays as the model wrote it (decision 0039). The reply marker `[message_id=<uuid>]` is parsed by `ui/src/replyMarker.ts`.

# Group triage and reactions

A group message that names no one is queued by the ingress transaction (`addUserRuns`) as a `triage` run when the group has two or more active members (`triage.go`, `triageSystemPrompt`). The run owner is the Bot the older rule picks (Primary Assistant, else random), so `routeAfterFailedTriage` (called from `failRun` and the engine-error path) can hand the message to a default member when the background model fails or answers invalidly; the chosen member answers as an ordinary `group_chat` run (`AddHandoff` with sender `system`, which publishes no chat message and no message event; triage runs are excluded from `WorkingBotIDs`). The model call never runs inside ingress. Settings: `group_triage` (default on) and `group_triage_model` (default the background/triage model); off restores the older rule exactly. Follow-ups (B12, reworked by B15): a message that names no one is always triaged, also while a member works on the person's previous message. When setting `group_followup_to_working` (default on) is on, the triage prompt gains a list of the members working now (`workingMembers` in `steer.go`: member, the person message its run handles, task title, start time; run running, queued or parked on a question and not yet answered) and a steer rule; the answer `{"bot_id":X,"steer":true}` (`parseTriageDecision`) queues the message as steering for X's running run (`steerTriagedMessage`, `bot_inbox` `user_message`, decision 0062), any other answer is a new request (a busy member takes it from its lane). A steer answer whose run has already answered finds no run and starts a normal run for X (continuation); a failed or invalid triage falls back to the member working on the most recent person message (`routeAfterFailedTriage`), else the default member. Ingress makes no steering decision for an unaddressed message and does not cancel the stand-in owner's queued work while a member works. Setting off: plain triage, no list, no steer option (a chosen member that works takes the message as queued input, as before). The triage answer may be JSON with a `brief` (`parseTriageAnswer`): a one-line restatement with references resolved, stored as the task title (`storeTriageBrief`) and shown in `[task record]`; the member's history already runs up to and including the person's message.

A person's reaction on a Bot's group message wakes that Bot once per 10-second window (`reaction_wake.go`: `noteReactionWake` -> `AddReactionWake`, a `group_mention` run with `run_wakes.source='reaction'`, no parent, no reply required); a Bot's reaction never wakes anyone, and an archived or departed author is skipped. Reactions reach the model only as a `[reactions: ...]` line under each message in the history window (`Store.reactionSummaries`), never in the system prompt. A reaction never changes task state. See decision 0060.

# Browser engine (Playwright MCP)

Workspace setting `browser_engine` (`playwright` default since 2026-10-30 | `classic`, Settings > Automatic behavior > Computer, env `TOFI_BROWSER_ENGINE`; `automationItems`, `internal/app/browser_engine.go`). With `playwright`, `microVMTools` registers the `browser_*` tools (`browserEngineSpecs`: snapshot, navigate, navigate_back, click, type, fill_form, select_option, press_key, hover, wait_for, tabs, file_upload, handle_dialog) plus the engine's own `computer_help` browser topic and prompt line; `computer_browser` stays registered with a "Fallback only" description prefix (`computerBrowserFallbackNote`). The prompt line (`computerBrowserEssentialsPlaywright`) must stay no longer than the classic one: the prompt-size caps in `prompt_budget_test.go` were measured with classic. Each tool relays to the guest action `browser.mcp {tool, arguments}` (in `microVMActions`, the lifecycle timeout list, `desktopNeedsSession`, the input gate and the tab cap, so it takes the desktop lease, starts the desktop and honours a person's takeover like `browser.navigate`). The guest (`internal/computer/guest/playwright*.go`) runs the pinned `@playwright/mcp` (`deploy/microvm/playwright-mcp`, installed by the image with `npm ci --ignore-scripts` into `/usr/local/lib/tofi-playwright`; node 22 is already in the image) as one stdio process, started on the first call with `--cdp-endpoint http://127.0.0.1:<Chrome port>` so the shared Chrome profile and its logins are the ones used; a new Chrome (new port), a crash or 10 idle minutes replace it, a desktop stop ends it. The guest relays only the allowlist `playwrightTools` (no evaluate, no run-code, no network or console dump, no `filename`), checks every argument key, accepts http/https URLs only, and confines `browser_file_upload` to regular files inside `/workspace` outside `browser/`, `.tofi-env`, `.ssh`, `.gnupg`, `.aws` (symlinks resolved; same limits as `browser.upload`). The server saves the page snapshot to a file after an action; the guest inlines it (`playwrightTidy`, only from its own output directory) and drops the echoed script, so the result of an action carries the new snapshot. Model argument `ref` is sent as the engine's `target`.
Review is the same path as `computer_browser`: the model declares `effect` on click/type/key/select/fill_form/dialog/upload; a consequential effect goes through `guardAction` (reviewer, `request_approval` when it says confirm, single-use approval refunded by `settle` when the engine reports a stale ref, which comes back as a `not_executed` repairable refusal). The reviewer sees the element name the model gave and the page URL and title learned from the last result. An upload is reviewed as `send` at least. Observation tools (`browser_snapshot`, navigate, wait_for, tabs, hover) are `Observation` risk in the recovery identity and in the scheduled effect fence; the others are effects. Benchmark: Anthropic's Claude Code docs recommend Playwright MCP for browser work; deviations are the allowlist above, the inlined snapshot, the `effect` and `element` arguments the review needs, and no screenshot tool (use `computer_desktop`). Default and fallback (decision 2026-10-30, after the live bench: Playwright 3.8 steps / 30 s against classic 18.5 / 107 s, both 4 of 4). The store keeps only what a person chose (`automation_settings`; `autoStored` tells unset from `classic`), so an account that never set `browser_engine` follows the default and an account that chose `classic` keeps it; Settings shows a "Default changed" note on the row while the item follows the default. Classic is the fallback path (`browserClassicFallback`): when the relay cannot start (`browserEngineUnavailable`: image too old, node or package missing, relay stopped, DevTools unreachable after the one desktop restart) the Bot's `browser_navigate` and `browser_snapshot` run through `computer_browser` (`browser.navigate`, `browser.read`) for `browserFallbackWindow` (10 minutes, per Bot, `Server.browserFallbackAt`), the other `browser_*` calls are refused unexecuted with a pointer to `computer_browser`, the failure goes to the log, and the first fallback result of a run carries a note. A snapshot with no `[ref=` falls back for that call only. The classic engine stays as the fallback. The benchmark (`scripts/browser-bench/bench.py`: four browser tasks, both browser engines (it also holds the desktop tasks, see Desktop engine), success from fixture-site records, steps and seconds, over HTTP with a cookie file) has been run with a real model on a real host. Proof so far: arm64 test host, computer image container, real Chromium: form, select, table, file chooser upload and stale-ref error through the guest relay (`TOFI_PLAYWRIGHT_E2E=1 go test ./internal/computer/guest -run PlaywrightRealChrome`), and `browser.mcp` through the guest action path on the real desktop as uid 1000 (`-run ThroughTheGuestAction`; docker needs `--security-opt seccomp=unconfined apparmor=unconfined` for Chromium's sandbox): first call 10 s with the desktop start, later calls 0.05 to 0.8 s, and the classic `browser.snapshot` sees the relay's tab. A guest built before this needs the new image (`unsupported action: browser.mcp` becomes a "needs a newer computer image" refusal). Image cost: about 19 MB on disk (`playwright-core` 14 MB, `playwright` 5 MB).

# Desktop engine (open-computer-use)

Workspace setting `desktop_engine` (`classic` default | `a11y`, Settings > Automatic behavior > Computer, env `TOFI_DESKTOP_ENGINE`; `automationItems`, `internal/app/desktop_engine.go`). It is independent of `browser_engine`. With `a11y`, `microVMTools` is hybrid: it keeps every classic tool (`computer_desktop` screenshots, pixel clicks, start and stop stay; its description starts with `computerDesktopHybridNote`: the tree is preferred, coordinates are the fallback) and adds `desktop_list_apps`, `desktop_get_app_state`, `desktop_click`, `desktop_set_value`, `desktop_type_text`, `desktop_press_key`, `desktop_scroll`, `desktop_secondary_action` (`desktopEngineSpecs`), a `desktop` topic in `computer_help` and one prompt line. Each relays to the guest action `desktop.mcp {tool, arguments}` (in `microVMActions`, the lifecycle timeout list, `desktopNeedsSession` and the input gate). Model argument `ref` is sent as the engine's `element_index`; `element` (a name for the review) is not sent. Review is the browser path: the model declares `effect` on click, set_value, type_text, press_key and secondary_action; a consequential effect goes through `guardAction` (the reviewer sees kind, element name or typed text and the app name as the page title). `desktop_get_app_state`, `desktop_list_apps` and `desktop_scroll` are `Observation`. The engine's `unknown element_index` / `appNotFound` answers come back as a `not_executed` repairable refusal, so a single-use approval is refunded by `settle`. An empty `value` is allowed (it clears a field). Drag, coordinate clicks and the click/key/window-placement methods are not exposed.
Guest. The desktop starts one `dbus-daemon` at `<runtime dir>/bus` (`desktop_bus_linux.go`) before Xvfb; every graphical process (fluxbox, the dock, Chrome, the Files launcher, the terminal shell) gets `DBUS_SESSION_BUS_ADDRESS`, `XDG_RUNTIME_DIR`, `GTK_A11Y=atspi`, `NO_AT_BRIDGE=0`, Qt accessibility switches (`desktopA11yEnv`). The Files launcher no longer runs `dbus-run-session`; the AT-SPI bus and registry start on first use through the bus's service activation. The bus is stopped last with the desktop. `internal/computer/guest/ocu*.go` runs the pinned open-computer-use as `open-computer-use mcp` on stdio (`startStdioMCP`, shared with the Playwright relay), one process per Bot (element indexes live in the process), started on the first call with the desktop's display and bus, replaced after a crash or a new desktop, stopped after 10 idle minutes and on desktop stop; replies are routed by JSON-RPC id. Allowlist `ocuTools` with per-tool argument keys (`checkOCUCall`: no `x`/`y`, `click_method`, `key_method`, `window_placement`, no drag); screenshots are dropped from results (`images_omitted`), text is cut at 200 KiB. A guest built before this answers `unsupported action: desktop.mcp`, which becomes a "needs a newer computer image" refusal.
Image. `deploy/microvm/Dockerfile` installs `python3-gi gir1.2-atspi-2.0 at-spi2-core` (8 packages, 8.3 MiB installed) and the release `v1.1.2` tarball of `iFurySt/open-computer-use` (arm64 and amd64, sha256 pinned in `OCU_SHA256_*`; 2.1 MiB binary, built from commit 531c9d4) to `/usr/local/bin/open-computer-use`; about 10.5 MiB in all. To update: change `OCU_VERSION` and both sums from the release's `SHA256SUMS`, and re-run the proof below.
Proof (arm64 test host, computer image container as uid 1000, `TOFI_OCU_E2E=1 TOFI_OCU_BINARY=... go test ./internal/computer/guest -run DesktopEngineThroughTheGuestAction`; the test starts the real desktop through `desktop.start`, the dock's Files launcher and a second GTK app on the same bus): one `list_apps` shows pcmanfm and the editor together, `get_app_state` returns each tree (about 320 lines, 25 KB for either), `click` on a menu of the file manager and `set_value` on the editor's text view succeed through `desktop.mcp` and the new text is in the next tree, a stale index is an engine error, `desktop.capture` still returns a screenshot, a desktop stop ends the engine process. Calls take 0.8 to 2.8 s (each spawns a Python AT-SPI reader). The GTK Preferences dialog works end to end: Edit > Preferences, the check box, Close writes `single_click=1` to `$HOME/.config/libfm/libfm.conf` (the bench's `desktop_setting` task checks that file).
Check state. The engine's tree does not print whether a check box or toggle is on, so the guest adds it: after a result, `desktopMCP` reads the app's active window over AT-SPI (`ocu_states_linux.go`; python3-gi is in the image; CHECKED or PRESSED, INDETERMINATE) and appends `[checked]`, `[unchecked]` or `[mixed]` to every check box, toggle button, switch and radio line (`annotateCheckStates`, `ocu_tree.go`). The states are applied only when they pair one to one with the checkable lines by count and name; otherwise the tree stays as the engine printed it. The line shape (indentation, `index role label`) is taken from the host-side fixtures; it has not been checked against the real engine's output on a real desktop. Limits. Chrome gets the bus but its tree needs `--force-renderer-accessibility` (not set: the browser stays with Playwright, and the flag costs renderer memory); xterm has no tree; LibreOffice is untested; menus are listed with off-screen frames. A tree is large (the context cost is the main risk for a long run): `desktop_get_app_state` takes `max_tree_depth` and `max_tree_nodes`, and the guest prunes any result over `ocuTreeBudget` (20 KB, so the Bot stays well under 25 KB; `pruneOCUTree`, `ocu_prune.go`): elements with a bracketed off-screen, invisible or hidden state and unlabeled decorative leaves (separator, image, filler and similar) go, a chain of unlabeled containers with one child collapses, a parent with many children keeps its first ones (60, then 30, 15, 8, 4 until the text fits) and an `… N more elements not shown` line, then depth is cut. Element indexes are never renumbered. A note line gives the sizes before and after. Test: `TestLargeTreeIsPrunedWellUnderTheLimit` (a 320 KB fixture). Apps a Bot starts from a shell need the display and the bus in their environment (the terminal shell has them, `computer_shell` does not). Benchmark: `scripts/browser-bench/bench.py` runs `desktop_folder`, `desktop_setting` and `desktop_read` once per `desktop_engine` (`--desktop-engines classic,a11y`; success from the file manager's saved file or the known file size, never from a model's opinion); live bench (2026-10-30, real model): a11y 13.7 steps / 71.8 s, classic 15.7 / 63.0 s, both 3 of 3, so the default stays `classic` (owner decision); the browser bench gave Playwright 3.8 steps / 30 s against classic 18.5 / 107 s, both 4 of 4, which made Playwright the browser default.

# Work trace (line B of divide-and-trace)

Design: `docs/design/divide-and-trace.md` (local). Every screenshot that passes the server on its way to a Bot is kept as a small picture of the run, so the person can review the screen work and the Bot can check its own sequence. System behavior, not a tool the model must call.
Capture point. `computer_desktop` `desktop.capture` and `computer_browser` `browser.snapshot` end in `afterComputerAction` -> `finishCapture` (`run_captures.go`, `capture_detail.go`). Order: note the page URL; refuse while a takeover card of the run is open (`takeover_active`: nothing stored, the Bot gets nothing); scale for `detail`; if `work_trace` is on, decide privacy, store, insert the `run_captures` row; add `capture_seq` to the result. Playwright `browser_*` tools return no screenshots, so after a call that can change the page (navigate, back, click, type, fill_form, select_option, press_key, file_upload, handle_dialog, tabs new/select) `engineTraceCapture` asks the guest for the classic `browser.snapshot` screenshot (no Guest change), and stores it (`detail` `background`). It runs in a goroutine, off the tool call (at most `traceInflightMax` 2 at once, a busy server drops the picture; `finalizeRunTrace` and `desktop.trace` wait up to 5 s for a run's pending ones), with source `viewer`, so the guest's `applyTabCap` drains no `tab_limit_note` meant for the model and `needs_observation` is untouched; the step label is taken when the call ends. The privacy decision uses the page that snapshot names, after it returns. It is never returned to the model, costs no tokens, does not count toward the 16 views, is skipped during a takeover, is rate-limited to one stored capture per 2 s per run, takes at most 48 of a run's 60 pictures (`traceBackgroundPerRunMax`), and its failure never fails the tool call. `noteEngineTrace` feeds the label, the page URL and the end of the secret window on `browser_navigate`.
`detail` (B1): `overview | full`, default `full`, on both tools. The host decodes the guest PNG and re-encodes it (overview: long side 640, JPEG q75, result `width/height/source_width/source_height/detail`); the guest is not changed and gets the same args, so no Guest rebuild. Click coordinates keep working through `screenshot_width/height`. Descriptions stay under the 1024-byte provider limit (`TestBuiltInToolDescriptionsFitProviderLimit`): long guidance goes in parameter descriptions.
Privacy, decided BEFORE a picture is stored (`traceRedaction`): (1) secret window, keyed by the COMPUTER (`computer_secret_windows`, the screen is shared by every run and Bot): opened when `AnswerUserForm` creates a private reference (same transaction) and BEFORE `applyFormSecret` types (closed again if the type fails and it was not open before), closed only by the next successful navigation (`browser.navigate`, `browser.action` navigate, `browser_navigate`), by `desktop.stop`, or after 15 minutes (`secretWindowMax`); it survives run end and covers other runs and Bots; (2) private origin: an origin a vault `browser_form` secret is bound to (kept in `trace_bound_origins` when the form is answered, so it protects later runs too), or an entry of `trace_private_origins` (an entry with a scheme is one origin; without, a host and its subdomains; the page URL is read AT CAPTURE TIME: a `browser.snapshot` result names it, and for `desktop.capture` the server asks the guest with a `viewer`-source `browser.snapshot` (`resolveTracePage`), only while some origin rule exists; a page that cannot be resolved counts as private and the capture is stored redacted); a redacted capture writes a row with `redacted=1`, no attachment, and the Bot still receives its screenshot; (3) takeover (above). Labels carry an action word, coordinates, a host or a cut visible text (`traceActionLabel`: typed text only as a character count, a one-character key as `key`, URLs reduced to the host, `redactContextText` on any text). There is no pixel redaction and none is promised; the manual page says so. At most 60 pictures per run (`limit` rows keep the number), 120 KB each, long side 640, JPEG.
Tables (additive, `run_captures.go`, `run_traces.go`): `run_captures(run_id, seq, call_id, attachment_id, taken_at, tool, action, label, detail, redacted, reason, width, height)` with `seq` assigned by the insert (`MAX+1`); `computer_secret_windows(computer_id, run_id, opened_at)`, `trace_bound_origins(origin)`; `run_traces(run_id, attachment_id, tiles, steps, created_at)`. Pictures are `attachments` with `origin='trace'` and no message binding, so no message, Artifacts list or guest sync sees them (they count in the `uploads` storage class). Settings (`automationItems`, group computer): `work_trace` (default on; off = nothing stored, no row, `capture_seq` absent, `desktop.trace` answers `work_trace_off`), `trace_retention_days` (default 7, 0 to 90, 0 keeps all; `cleanupRunTraces` runs with the task retention sweep), `trace_private_origins` (new kind `text`, one entry per line, normalized; a change is a confirm-class change for the settings tool because a shorter list keeps more).
`desktop.trace` (B3, `trace_action.go`): a `computer_desktop` action (also `trace`) with `last` (2..9, default 6), `capture_seqs` (at most 9) and `columns` (2..3). It joins stored captures of this run, takes no screenshot and does not use the computer or its lease, answers an image (`image_url`, `tiles`) that the vision path lifts like `files.view`, and counts toward the 16 views per run (`viewed` is shared with `files.view`). Redacted and unkept steps are grey cells. `montage.go` is the one stitching code: 424x265 tiles, 18 px label line `#seq +m:ss label` (built-in 7x13 bitmap face, ASCII only), 3 columns = 1280 px wide, JPEG at most 640 KiB. The model gets at most 9 tiles, the person at most 12.
Strip for the person (B4, `run_trace_strip.go`): `execute`'s deferred hook calls `finalizeRunTrace` when a run ends (any end state): it frees the run's memory notes (the secret window stays), and with `work_trace` on and at least two captures (and one kept picture) stitches the last 12 (11 plus a "... N earlier steps" cell when there are more) into `run_traces`, then sends a `run` event carrying `Run.trace`. `GET /api/runs/{id}/captures` lists the rows (`captures`, `trace`); `DELETE` removes pictures, rows and strip (a run still going keeps its rows as empty steps, reason `deleted`, so `capture_seq` never restarts). Runs read by `Runs` and the paged list carry `trace` (`decorateRunTraces`). Exports leave `origin='trace'` out (`snapshotPortableAttachments` and its count); retention ages a run that has a strip by the strip's `created_at` (pictures, rows and strip go together, so a cell never names a missing step) and a run without one by each picture's `taken_at`.
UI. `WorkTrace.tsx` (lazy; `React.lazy` from `TaskActivityBody.tsx`, so it sits at the end of a run's opened Activity list, or, when that run's Activity list is not drawn (Activity hidden, or no task block), under the run's final reply bubble (`traceUnderReply` in `workTraceLayout.ts`, rendered by the timeline row from `Run.trace`; never in both places), and from `ScheduledTaskRow.tsx` in a schedule's record) shows a `process-line` with up to six thumbnails cut from the one strip by CSS (`workTraceLayout.ts`: the grid numbers must equal `montage.go`, `test:work-trace` compares them), opens the strip in `AttachmentLightbox` (new optional `cellAt` prop: a click on a step shows that step's picture, a click on that picture goes back), and deletes the trace in two steps. The line is the only addition to the final chat message, and only when Activity is not drawn for that run; the run list already carries `trace`, so no extra read. Tests: `go test ./internal/app -run 'Capture|Overview|WorkTrace|DesktopTrace|Montage|Strip|Retention|Exports'`, `npm --prefix ui run test:work-trace`. Manual: `computer/work-trace`, failure pages `takeover_active`, `work_trace_off`.

# Settings tool and manual

Design: `docs/design/bot-settings-and-manual.md` (local). The settings registry (`internal/app/settings_registry.go`) is the single source of truth for what a Bot may read or change: key, scope (`account|bot|conversation|connection|system`), kind, allowed values, risk class (`direct|confirm|forbidden`; `RiskSpec` has Self, Other and Loosen), deep link and manual page. `automation.*` entries are built from `automationItems` (a new automatic behavior needs no second edit). `go generate ./internal/app` runs `cmd/tofi-settings-registry` and writes `ui/src/generated/settingsRegistry.json` and the manual's reference pages under `internal/manual/generated/`; `TestSettingsRegistryGenerated` fails when they are stale. The page and section lists in the registry (`settingsTabPages`, `botSettingsPages`, `groupSettingsPages`) must match `ui/src/settings/sections.ts`; `npm --prefix ui run test:settings-registry` checks links, tabs and the section ids in the components.
Deep links are relative paths (`MessageMarkdown` keeps them; a custom scheme would be dropped): `/settings/<tab>#<section>`, `/settings/connections/<name>[?tool=][#section]`, `/b/<id>/settings#<section>`, `/g/<id>/settings#<section>`, `/b/<id>?side=<view>`. `ui/src/settingsRoute.ts` is the pure reader; `MarkdownLink` hands a same-origin match to `openDeepLink` (`settings/deepLinks.ts`, event `tofi:open-link`); the address `/settings/...` is read by `readConversationRoute`, the cover opens once the index is loaded and the address goes back to the conversation (`useConversationNavigation`). A section is reached by `data-section` (`SettingsSection id`, `SectionAnchor`) and flashed with `data-jump-target` (`settings/sectionJump.ts`). An id not in the account's index opens nothing. Tests: `test:settings-route`, `test:settings-registry`, `test:settings-deeplinks`. The entry reads only the cheap address test (`conversationRoute.ts`, `isSettingsHref` in `MessageMarkdown.tsx`); the route reader, the section lists and the opener are lazy (`settings/linkRuntime.ts`, loaded on the first link; the app hands it `OpenLinkDeps` through `provideLinkDeps`). Do not import `settings/sections.ts` or `settingsRoute.ts` from entry code (`test:shell-budget`).
The `settings` tool (always declared; `settings_tool.go`, `settings_read.go`, `settings_write.go`, `settings_writers.go`, `settings_gate.go`, `settings_changes.go`) has actions `list`, `get`, `set`, `revert`, `status`. A binding (`settingBindings`) joins a registry key to its reader and writer; the writers call the Store or Server method that already owns the change. Results are bounded (16 KiB) and every row carries its change class, the link and a label worded from the person's language (`internal/manual` term tables, generated). Reads work in every run. Writes need an attended run (`runAttended`: the conversation is user-visible, no schedule is in the run's ancestry, and a person's message started it or an ancestor); an unattended run is refused with `settings_change_needs_owner`. A direct change is recorded in `settings_changes` (row first, marked applied after the write; values cut at 4 KiB are not revertable), posts a `settings_change` notice (system, kind notice, outside the Bot's history) with Undo, and counts toward `settings_change_limit` per run (default 8; only the person changes it: that automation key is forbidden to the tool). Undo is `settings(revert)` or `POST /api/settings-changes/{id}/revert` (owner session); it restores the old value only while the setting still holds the value the change wrote (`settings_changed_since`). `GET /api/settings-changes` feeds Settings > System > Data > Changes by Bots. Forbidden keys (secrets and keys, providers, update, data, purge, accounts, computer resources, sign-out, the change cap) return `settings_forbidden` with the page link and no value. A confirm-class change uses the existing approval rendezvous (`settings_gate.go`, the extension gate pattern): `settings(set)` refuses with `settings_change_needs_approval` and a token `setting <key> <target> #<digest>` (the digest covers key, target, new value and, for a revert, the change reverted); the server remembers facts it built (`ApprovalFacts.Setting`: label key, target name, old and new text, effect code, link, loosens) for that run and token; the Bot asks with `request_approval` (target = token; `gateFactsForTarget` attaches the facts; a token the server did not issue in this run is `setting_change_unknown`); after the person approves, the same call runs once (`claimApproval`), is recorded with the card's question id, and the approval is given back when the write fails with certainty (`not_executed`). A declined card blocks the same change for the rest of the run (`settings_change_denied`). The card never offers Remember or Always allow, and no reviewer decides it. UI: `extensionFacts.tsx` words the rows (effect codes `record.facts.effects.*` in 7 locales; the server sentence is the fallback for a code a build does not know). The product manual (`internal/manual`, tool `manual` in `manual_tool.go`) is read on demand: the prompt has one line (`runtimeCapabilityPrompt`), `index` lists guides and reference pages, `read` loads one page, `search` is a substring match, `explain` takes a failure code, `whats_new` returns the release notes of the installed version. Pages are English Markdown with front matter (`id`, `title`, `summary`, `link`, `kind`, `see_also`). Guides and failure pages are written by hand in `internal/manual/pages/` (a `failures/<code>.md` for every stable code a person or Bot meets: schedule, update, settings, gate and connection codes, listed by `manualFailureCodes` in `manual_test.go`, which fails for a code without a page and for a page without a source); reference pages, the release-notes copies (`whats-new/<version>`) and the term tables are generated into `internal/manual/generated/` by `go generate ./internal/app`. The screen's words are put in the page when it is read: write `{{ui:namespace:key}}` (a locale catalog key) and the person's language fills it, falling back to English; the generator reads the keys the guides use, so a new `{{ui:...}}` needs no second edit. `{bot}` and `{group}` in links are filled from the run. A page with a link has the line "Open this page:"; every link in a page must resolve (`TestManualTextAndLinks`). Release notes are tracked: `release-notes/<version>.md` (front matter `version`, `date`, `channel`; short, Simplified Technical English, what people see). The release workflow's `version` job runs `scripts/check-release-notes.sh "$TAG"` and fails a `v*` tag without its file; `ci.yml` and `ci-local.sh` run `--all`. Write the file in the commit that prepares the release, then run `go generate ./internal/app`.
A Bot's look and the theme are server state (owner 2026-10-28, S7): `bots.avatar` (added by `migrateBotAvatar`; JSON `{schemaVersion, shape, pattern, palette}`, validated by `normalizeAvatar` against `internal/app/avatar_catalog.json`, which `test:avatar-store` keeps equal to `ui/src/lib/tofi-avatar`; read at API time by `withEffectiveModels`, never by `scanBot`; `PATCH /api/bots/{id}` takes `avatar`, `null` clears; export and import carry it in `portableBot.Avatar`) and `user_preferences.appearance` (`system|light|dark`, empty = never chosen; `GET|PUT /api/preferences`). Keys `bot.avatar` (own = direct, another Bot = confirm) and `account.appearance` (direct). The browser keeps its copy for the first paint (`avatarStore.ts`, `tofi:appearance`); the lazy modules `avatarSync.ts` and `appearanceSync.ts` reconcile it after sign-in: a stored look or theme wins, and a copy the server does not have yet is handed up once (the migration of what people chose before). They take `request` as an argument and must not import `api.ts` or `avatarStore.ts`: a lazy chunk that does reshuffles the entry bundle and breaks `test:shell-budget` (measured: +3 eager files, +900 B gzip).
The older workspace tools (`workspace_update_bot`, `workspace_update_group`, `workspace_delete_bot`, `workspace_delete_group`; on demand, kept one version) are aliases: each field is one settings change through `settingRun.aliasSet`, so they meet the same classes, cards and attended-run rule; `workspace_list` only reads. Group `expected_name` and `expected_bot_ids` still guard against another client, except for a field the call already put in place (the call is repeated after the card). Connections (S8): `connection.connect` changes nothing and returns the status, the page and the next step (`request_connection` in a conversation a person can see, the link otherwise); `connection.enabled` (pause and resume) and a tool mark made stricter (`connection.tool_tier`) are direct, audited and revertable; `connection.disconnect` is the Settings sign-out path (`OAuthDisconnect`, then the standing allowances of the server are revoked as `deleteMCPServer` does) and needs a card; a looser tool mark needs a card, and so does the revert of a tightening, because the class of a revert is computed again for the reverse direction. Owner decisions: own Bot = direct, another Bot = confirm; connection access lists, approval mode (both directions), model and effort, archive and delete of a Bot or conversation, group members, disconnect and loosening a tool tier = confirm; unattended runs write nothing.

# Desktop UI artifact and version skew

The desktop app (private repo tofi-app) bundles a copy of the Web UI build instead of loading the server's live UI, so the bundled UI and the server can differ in version.
- Every release tag publishes `tofi-desktop-ui-<tag>.tar.gz` and `.sha256` (release.yml, job `desktop-ui`), built by `node scripts/export-desktop-ui.cjs OUT --version <tag>` from the tag's commit. Its `ui-artifact.json` carries `server_version`, `revision` and `desktop_contract`.
- `internal/app/desktop_contract.go` defines `DesktopContract` (integer, the only place) and `DesktopMinClient` (x.y.z). `/api/server-info` (single and accounts mode) returns `"desktop": {"contract": N, "min_client": "x.y.z"}`; the export script reads the same constant.
- **Bump `DesktopContract` whenever the UI <-> server API changes incompatibly** (a route, field or event the shipped UI needs is removed or changes meaning, or a new UI needs an API an old server lacks in a way that cannot degrade). Raise `DesktopMinClient` when the desktop shell itself (not the UI) must be newer. Additive changes need neither. The desktop refuses to open a workspace when the contract differs or its version is below `min_client`, and offers its updater plus "Open in browser".

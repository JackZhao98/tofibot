# Bounded Notion leaf adapter candidate

This branch adds a separately reviewed source candidate behind explicit private Runner configuration. It does not add a catalog preset, installer field, package installation, account connection or production deployment. The original generic Runner remains latest-only.

The one accepted profile declares vendor source `@notionhq/notion-mcp-server` version `2.5.2`, upstream revision `730ae781ba28beeaf0865025a3f2ed4c25ea2387`, TOFI adapter revision `notion-stdio-v1` and exact leaf protocol `2025-11-25`. The package declaration comes from [the pinned vendor source](https://github.com/makenotion/notion-mcp-server/blob/730ae781ba28beeaf0865025a3f2ed4c25ea2387/package.json); it is not proof of a published package or installed bytes. Published artifact ownership/integrity, actual runtime compatibility and package behavior remain unverified. The attempted public registry metadata read was unavailable. Do not declare this provider usable until that independent verification and candidate review finish.

`Spec.Adapter` is private operator input. Ordinary installation JSON rejects this field and cannot opt arbitrary packages into an older protocol. No production configuration opts into it. The profile requires `NOTION_TOKEN` through the existing absolute private secret-file mapping; embedded token environment values are rejected, and startup requires a mode-0600 regular token file. Secret values do not enter the adapter identity.

The leaf explicitly initializes `2025-11-25`; it never probes or automatically falls back. The SDK's returned version must match before `tools/list`. Its optional client capabilities and automatic multi-round-trip interactions are disabled. Request state, input responses and optional metadata/extensions are rejected before leaf startup/call and again at the wire boundary. Unexpected interaction results fail without replay. The bridge translates basic named tool requests and schemas only.

Server-to-Runner stays authenticated private Streamable HTTP at `2026-07-28`. A SHA-256 identity of adapter/package/source/protocol and invocation appears in authenticated status and the private bridge URL's `tofi_adapter` query. Missing or stale identities fail before starting a child. Attachment reads that identity through the existing authenticated status API. The URL already participates in configuration, metadata and schema fingerprints, so reattachment invalidates old schema references and binds new approval requests to the new identity. Existing model-visible approvals, owner-only trusted read-only names, allow/deny rules and one-time/no-replay behavior are unchanged. A stale prepared call cannot reach a changed bridge identity even if its old approval is answered; this patch does not redesign automatic cancellation of pending questions.

Requests also bind the selected plugin instance through schema discovery, actual RPC dispatch and process acquisition. The cached HTTP handler validates and retains that same registered instance after body parsing, including `server/discover` and `tools/list`; its tool callback never resolves a replacement by ID. Private call/schema routes use the same bound acquisition. Removal rejects active leases and marks an idle instance as retiring under the busy-check mutex before shutdown or manifest writes. A failed removal restores the original registered instance. An old in-flight request fails after removal even when the replacement declares the same adapter identity, and cannot start or call its replacement.

Synthetic tests run the authored Go test helper over stdio and disposable HTTP fixtures, with no provider package, live token or external account request. They cover exact-version rejection before listing; normal outer modern discovery; unsupported field rejection before execution; private token modes; profile/source pin validation; immutable copied policy; stale identity rejection; lost-response no replay; authenticated attachment; changed schema references and approval fingerprints; and existing human-approval denial/one-use controls. Deterministic replacement tests pause actual HTTP body reads, use real removal and synthetic final registry publication, then require stale call/list/discover/private-call rejection with zero replacement methods and successful fresh calls. Both changed and identical adapter policy replacements are covered, as are acquisition during shutdown, busy leases, cancellation and recovery from failed removal. A fixture's read-only hint grants no exemption.

Remaining scope: verify the actual published package and runtime in an independently authorized task, review this immutable candidate, then separately decide installation/catalog activation. None of those steps is implied by source tests.

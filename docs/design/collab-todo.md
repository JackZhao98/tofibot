## C1 设计：等待、消息与任务（2026-10-23 owner 与对标后定稿的部分）

目标：把真人团队里的协作拆成一个工作流状态机，对标并超越 Claude Code Agent Teams、A2A、Anthropic 多智能体研究系统。

**已定**

1. **等待 = 异步调用。** 等 Bot 回话、等命令、等人、等时间，本质都是“发出调用，结果晚点到”。异步调用马上返回回执，结果作为事件送回。现有三套（`follow_up`/`run_waits`、委派回传、B1 最后完成者回传）收编为一套。可以同时挂多个等待，也可以编组“全部到齐再处理”；等的过程中可以先跟用户说一句。
2. **消息 + 任务状态。** 消息负责沟通：通用私聊骨架，一对一、一对多、Bot 对 Bot 走同一个“收到消息”流程。任务负责记账：每件被派的活是一个任务对象，有状态（已提交 / 进行中 / 需要输入 / 完成 / 失败 / 取消）。界面能看到每个 Bot 有几件待办、进度如何。对标：Agent Teams 共享任务表 + 邮箱；A2A Task 生命周期。
3. **中途提问。** 子 Bot 有问题就发消息给派活的 Bot，任务状态同时变成“需要输入”（对标 A2A input-required）。
4. **冲突以用户为准，由系统同步。** 没有隶属关系，用户可以直接跟任何 Bot 说话。用户改了某个任务的需求，系统自动通知派活的 Bot，不靠模型记得转告（对标 A2A 任务更新推送）。
5. **进来的事件先挂起，不打断，进度不丢。** 用户新消息、子 Bot 结果、命令结束、超时，都先进收件箱；当前工具调用结束后 Bot 读到，带着它继续干。不再“取消 run、新 run 只拿摘要”（对标 Claude Code 排队插话；持久执行 Temporal/LangGraph 检查点）。
6. **一个 Bot 同一时间只干一件活。** 其他任务树派来的活排队或按轻重插队；同一任务树里派回来的活算这件事的一部分，不排队。
7. **停止照 Claude Code 做，连带取消子任务。** 两档：排队插话（默认），立即打断（按钮/急停，杀掉当前工具）。停一个 Bot 会连带停它派出的子任务（对标 Temporal 取消作用域）。
8. **等待的意识。** 每轮上下文列出在等什么、等多久、何时超时；Bot 能取消。`outcome=pending` 只有存在真实等待才算数。
9. **超时也是结果。** 到点把“超时”送回给 Bot 决定；等待落库，重启不丢；界面可见、可取消。
10. **死锁与空转。** 等待不锁收件箱（任何消息都能叫醒）；登记等待时查等待环，成环则登记失败并告诉模型先解开（对标数据库 wait-for 图）；连续几轮无进展上报给主 Bot 判断（对标 Magentic-One 停滞计数）；消息带“是否需要回复”标记，同一任务树有消息总量上限。

11. **主 Bot = 最先从用户手里接下这件事的 Bot**（任务树的根）。私聊里就是用户对接的那个 Bot；群里是被 @ 到或接了活的那个（群里的细节放到 C3 单独设计，“群固定组长”不在这里讨论）。主 Bot 负责收尾、接上报、判断要不要继续；负责人跟着任务走（对标 Agent Teams：谁建团队谁是 lead）。
12. **派活的 Bot“没了”。** run 失败或电脑重启不算没了：任务和等待落库，结果照常进它的收件箱叫醒它。被急停：按第 7 条连带取消。被删除或移出群：连带取消它派出的所有任务；删除前提示“还有 N 件任务在跑，会一起取消”（对标 Temporal 父关闭策略默认终止、Erlang 监督树）。
13. **过期结果：改需求不重开任务，版本号加一。** 改动作为消息送进正在跑的任务；结果带“基于第几版”，不是最新版就标“基于旧需求”，由主 Bot 决定沿用还是重做；任务结束后再改则开新任务（对标 A2A 终态不可变、乐观并发版本号）。
14. **清理机制。** 被取代的旧结果、已结束任务的大块产物到期清理，对话里保留一行摘要。保留期在设置里可见可改，默认值待定（参考：Temporal 按命名空间设保留期，Claude Code 会话记录默认 30 天）。

C1 讨论完毕；默认保留期与实施拆分待定。

## C2 设计：后台任务（2026-10-23）

C1 第 1 条（异步调用 + 回调）和第 5 条（排队插话，不打断）已覆盖 C2 的主体。C2 补充：

1. **两套叫醒并存。** 主信号：电脑侧在命令结束时主动上报（退出码、输出位置），作为事件送进 Bot 收件箱。备用：Bot 可以自己设一个定时“到点看一眼”（等进度、防主信号丢失）。主信号先到时，由 Bot 自己取消多余的定时。对标 Claude Code：后台命令结束自动通知；`ScheduleWakeup` 作长间隔兜底，主信号是 Monitor 或任务通知。
2. **电脑重启与休眠（超出 Claude Code，参照运维做法）。** 底线：重启后系统给每个受影响的等待送回“命令被重启中断，最后输出在此”，按 C1 第 9 条由 Bot 决定重跑或放弃。另外尽量不断：休眠保留内存状态；升级、重启电脑前先查有没有在跑的后台命令，有就等待或先问用户（对标 Kubernetes 节点排空；与 `tofi update` 先查在跑 run 同一规矩）。不做命令级检查点续跑。Claude Code 的后台命令随会话结束，不保证跨重启。

C2 讨论完毕。

## C4 设计：技能库与按 Bot 启用（2026-10-23，进行中）

对标：Claude.ai 设置里的技能库 + 开关；Claude Code 插件（一个插件打包多个技能）。

1. **一个全局技能库。** 不管谁装的（用户在设置里装，或聊天时让 Bot 装），装完都进库。
2. **每个 Bot 一列勾选。** 库里每个技能对应一个格子，勾上 = 这个 Bot 能用。
3. **Bot 装的技能只给自己打勾。** 别的 Bot 不自动获得。
4. **给别的 Bot 开有两条路。** 用户在 Bot 设置的技能页从整个库里勾选；或用户跟 Bot 说，Bot 浏览库并给自己打勾。Bot 给自己勾选库里已有技能不需要用户批准。
5. **单个技能与套装。** 套装是一组技能。界面以套装为主，整体开关；可以展开（嵌套列表）单独开关其中某一个。数据结构同样支持两层。
6. **没有“对所有 Bot 生效”的总开关。** 例外：官方出品的技能（文档类等）全局启用。
7. **官方技能可以对单个 Bot 关闭**，默认全部开启。
8. **界面要简单。** 参照 Codex 的技能页：一键添加，不堆选项；按 Bot 开关、套装展开等放在次一层。
9. **删除与更新。** 从库里删除只能由用户做；Bot 只能取消自己那一列的勾。Bot 更新自己装的技能用“发新版本”，不再删了重装（对标 Claude API 技能版本号）。
10. **可见。** 设置里能看到每个勾是谁、什么时候打的（Bot 可能自己发现并勾选技能），用户随时可取消。

C4 讨论完毕。**已实施**（2026-10-23，[D58](../decisions/0058-skill-library-per-bot.md)）：第 6 条“官方技能全局启用”落成“官方技能默认对每个 Bot 开、可按 Bot 关”，没有任何全局总开关；Bot 装技能不要批准、发新版本要批准（Q11）。

## C3 设计：群聊协作（2026-10-23，讨论中）

owner 判断：谁先接话不是大问题，现行分诊挑一个人就够。真正的问题是没有协作感：干一干就停，汇报没人接，人插话要等轮流说完，reaction 形同虚设。owner 要求做成通用能力，不落到某个具体提示词或脚本上。

**已定**

1. **任务可以由 Bot 发起。** 根一定能追溯到用户；Bot 可以把用户的话整理成需求发到群里，或再拆给别人。Bot 发起的任务，它就是派活的人（C1 第 11 条）。
2. **群里公开汇报即可。** 汇报要挂到所属任务上，发言等于提交，系统叫醒派活的 Bot 去审；审完决定继续推进。
3. **任务带清单，说“做完”要对账**（对标 Anthropic《Effective harnesses for long-running agents》）。清单每项有状态；一次做一项，做完只改这一项的状态；每项单独结束（完成 / 跳过 / 受阻，都写原因）——“没发现漏洞”是这一项的结论，不是整件事失败，接着做下一项。Bot 说做完但清单上还有没结束的项，退回一次（`pending` 退回的推广）。文章里的对应做法：功能清单 JSON 只许改 `passes` 状态、不许删改条目；进度文件 + git 记录做交接；只有验证过才标完成；主要失败模式是“过早宣布完成”。外部列表会更新：用 C1 等待外部变化或 C2 自设定时回看，不写专用脚本。
4. **会拆任务（divide and conquer）。** 用户只说一句“帮我搭个后端”，Bot 自己拆细节；进行中发现还能拆、或有能并发的部分（你写这个接口、他写那个），就拆出去并发，最后合并。任务之间可以有依赖，前置完成后自动解锁（对标 Agent Teams 任务依赖；Anthropic 研究系统：主导者拆任务，每个子任务写清目标、产出格式、工具与来源、边界；按复杂度定投入：简单 1 个 Agent，复杂可 10 个以上）。注意 Anthropic 的提醒：编码任务真正可并行的部分比研究少，依赖多时多 Agent 反而差——并发写代码前先定好接口约定。
5. **谁被叫醒。** 都能看到全部群聊；叫醒按以下规则：
   - 第一轮没人接活：走选择器（AutoGen 做法），按成员角色描述挑最适合这件事的人，不是挑“管事的”。**注意这是新要求**：现行代码没有模型分诊——没 @ 人的群消息给“主助理”（若在群里），否则随机一个成员（`defaultGroupRunSpecTx`，`internal/app/collaboration.go:279`）。成员名单和角色已在群上下文里（`context.go:913-926`）。例：问“今天特斯拉怎么样”，分给看股票的。想固定负责人，就在角色描述里写明“这个群里某类事归我接”，不另设群组长设置。
   - 二次分诊：接到活的 Bot 先判断适不适合自己（它知道群里都有谁、各自的描述）。合适就在群里说一声“这个我接了”，其他成员用 reaction 回应，大家都看得到，也就不会抢答；不合适就转给更合适的成员或上报（对标 OpenAI Agents SDK handoff 转交；Agent Teams 领取任务）。
   - 派活用 @，做完 @ 回派活人；被派的人从任务记录知道派活人是谁。
   - 就算没 @，被派 Bot 在这件任务里的每句话都由系统送进派活人收件箱（对标 Agent Teams 成员消息自动送 lead、A2A 任务更新推送）。只有三类叫醒派活人：提问、交结果、连续几轮无进展；普通进度更新放着，下次醒来一起读。派活人据此判断问用户还是自己拍板。

6. **串行单位从“群”改成“Bot”（对标 Actor 模型、AutoGen 新版、Agent Teams 成员各自独立会话）。** 现状：一个群一条工作线（`runConversationWorker`，`internal/app/collaboration.go:1088`），同时只跑一个 Bot；人插话时被 @ 那条线排队的活被取消、在跑的到间隙停下只留摘要，其他 Bot 在跑的不停、新消息排在后面，派活类队列优先级还更高——这就是“轮流回答”的根子。改为：每个 Bot 一条线（一次只干一件，C1 第 6 条），不同 Bot 并行；人插话进相关 Bot 收件箱，正在干同一件事就在间隙插入、不取消不丢进度（C1 第 5 条），闲着就立刻开工，不等别人。防乱靠分诊只挑一个 + 接活先声明、其他人 reaction 回应。与 C1 第 5 条同一处底层调度改动，一起做；要处理并发写库与群消息先后顺序。

7. **reaction 变成真信号。** 现状：Bot 能点（`react_to_message`，`internal/app/reaction_tool.go`），但别人点的 reaction 只记一条事件、不叫醒任何人，也没进 Bot 的对话上下文——单向通道。改为三层：(1) 看得见：消息上的 reaction（谁、何时、什么）进对话记录；(2) 会叫醒但不强制回：给 Bot 的消息点 reaction 低优先级叫醒它，它可以静默或回应；reaction 默认不需要回复，防止来回客套；(3) 提示词按原则讲清何时用：确认、同意、看到了、“我接了”用 reaction，不再发一句话。**reaction 不对应任务状态**：状态变化只走正式的接活和交结果（防止随手 ✅ 绕过第 3 条对账）。业界未见把 reaction 当 Agent 间正式信号的公开做法，这一块是往前走。

8. **界面：对话里的任务卡片。** 一件任务在对话里是一张卡片：标题、负责人、清单与每项状态，实时更新、不另刷消息（对标 Claude Code 对话内待办）。默认收起成一行“负责人 · 3/7 · 进行中”，点开看清单。Bot 身上的待办数、全局看板这次不做。

C3 讨论完毕。

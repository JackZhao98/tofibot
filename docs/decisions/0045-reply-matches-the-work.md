# 0045 回复要和做过的活对得上：范围与数字照工具记录，留下的东西说明在哪

> 编号 D45，索引见 [README](README.md)。

## 决定

Bot 的最终回复有两条通用要求，由提示词原则、工具说明和工具返回值一起承担，不针对任何任务：

1. **回复对工具记录成立。** 关于范围（全部、每一个、只有一部分）和数字（数的是什么）的陈述，必须恰好是工具结果能支持的；只查了一部分，就说查了哪一部分；动作只在结果确认之后才说做了。
2. **留下的东西要说明有什么、在哪。** 工作留下了人之后要依靠的东西（文件、存下的状态、定时任务、电脑上的位置），回复说清楚有什么、放在哪，位置用工具结果给出的那个。**只发布人要收的东西**：草稿、自检图这类工作文件留在电脑上，不进回复。

落点（按它们被读到的时刻排）：

- 写回复的那一刻：`say` 的说明里加一句（范围与数字照工具结果，留下的东西说明位置）。
- 工具工作之后、回复发出之前的那次完成复核（`taskCompletionFinalReminder`，以及两条定时任务的复核）：把“逐句对照工具记录”放在最前，“要的东西是否做完”放在后面；三处共用一段原则文字 `replyMatchesRecordPrinciple`。
- 工具返回值给出事实（Anthropic 的工具设计建议）：
  - `computer_files` 的写入结果新增 `location`：文件在电脑上的绝对路径。原先只回传调用时的相对路径，Bot 知道绝对路径也没有从结果里读到。
  - `publish_file` 的结果新增 `source_path`（从电脑上哪个路径发布的）和 `attached_to_reply`（这个 run 到目前为止挂在回复上的全部文件名，按发布顺序）；说明里写明“发布的东西人都会看到，只发布人要收的；草稿、检查和其他工作文件留在电脑上”。
  - `create_schedule` 的结果本来就带时区和用该时区写好的下次运行时间（`next_at_local`），不需要改。

## 为什么原来的复核没起作用（查证过程）

评测 `deliv-terra-r3`（线上 rc.32，Codex terra）：

| 问题 | 看到的 |
|---|---|
| 复核没触发？ | 触发了。发票和定价监测两个任务的记录里都有一次 `say(answer)` 被 `answer_review` 退回（工具集里有 `computer_shell` / `create_schedule` 之类的工作工具，复核已武装；`say` 本身不算工作）。 |
| terra 没看到？ | 看到了，而且照做了：发票任务退回后又跑了两次检查脚本；定价监测任务退回后改写了一遍回复。 |
| 那为什么还错？ | 复核问的是“要的东西做完没有”：对照用户请求里的交付物、字段、类别。它没有要求把**回复的每一句**拿去对工具记录；唯一接近的一句只谈“类别、来源、动作”，不谈范围量词和数字。所以发票任务的退回让模型多验证了 PDF，却没有回头改“所有发票都核对过明细”（只有 PDF 核对过）和“40 份”（去重后 35 份）。 |
| 为什么没提“在哪” | 复核和 `say` 说明里都没有“留下的东西说明位置”这条；`computer_files` 的结果只回传相对路径，监测任务里的基线位置模型自己写进了定时任务的指令，回复里却没写。 |
| 为什么会多发布 | `publish_file` 的说明没有说发布的一切都会跟着回复给人，也不列已经挂了什么；季度报告任务里模型把自检图 `layout_check.jpg` 一起发了。 |
| 位置够不够近 | 复核本身就是写回复那一刻的退回，位置已经是最近的；问题是内容，不是位置。 |

结论：缺的是内容（原则没覆盖“回复对记录”和“位置”）以及工具结果里的事实，不是触发时机或模型没看到。

## 实测（本机和重放，Sonnet 5.5；预算 $5，估价约 $3.9）

**本机端到端**（`main` 二进制 vs 本分支二进制；3 个与评测题无关的通用任务：带偏好的工作日提醒、一份往后要找回的清单、五家公司总部所在地的查数加“你查得有多彻底”；每项每边 3 轮；不评分，人工读回复和工具记录）：

- 本机没有电脑，`publish_file` / `computer_files` 不可用，测不到工具结果这半边；清单任务只用 `save_memory`（不武装复核），所以只有 `say` 说明在起作用。
- 调用数没变：提醒任务前后都是 4/4/5 次模型调用，复核各触发一次（以前后各 1 次计），没有新增模型调用；平均耗时 26.6 s → 22.1 s（噪声内）。
- 回复里“东西在哪”的说法：前后都只说“已存好 / 已记下”，没有更具体的位置（本机没有可引用的路径）。没有退步，也没有可见的进步。
- 数字与范围：数公司的任务，前后都说了“凭记忆，没查”，与记录相符（前 3/3，后 3/3；其中后一轮 1 次实际搜了，并如实描述了搜了什么）。

**重放探针**（把评测里 `deliv_watch_weekly` 的真实工具记录重放给 Sonnet 5.5，回复被 `answer_review` 退回之后看下一次回复；旧 = `main` 的复核文字、`say` 说明和工具结果，新 = 本分支；每边 3 次；重放里的重复读取返回上次的结果）：

| | 旧 | 新 |
|---|---|---|
| 回复里写出基线文件的位置 | 0/3 | 3/3（绝对路径，并说明也附在回复里） |
| 退回后又去重复读页面 / 重试 | 3/3（2 轮） | 0/3（1 轮） |
| 每次的输入 token | 约 7.3k（两轮） | 约 3.8k |

重放的局限：历史是照评测记录重建的，不是真实 run；重放里旧版的“重复读取”返回的是缓存，模型据此多写了一段对 `/pricing` 的猜测，那是重放的副作用，不算旧版的缺陷。可信的只是方向：位置从 0/3 到 3/3，退回后的反应从“再去做一遍”变成“改回复”。**线上还没有测**：真实效果要等部署后重跑 `deliv_*`（发票、监测、季度报告）。

## 守卫（测试）

`internal/app/reply_matches_work_test.go`（每条改回原样都会变红，已逐项验证）：

- 三条复核文字都含“逐句对照工具结果”“范围与数字恰好是结果支持的”“部分检查报告为部分”“数字说明数的是什么”“说明有什么、在哪，用工具结果给的位置”“工作文件留在电脑上”，不含示例或对比措辞；回复对记录的检查在完成度检查之前。
- `say` 说明含范围与数字、位置两句。
- `publish_file` 的结果含 `source_path` 和 `attached_to_reply`（先后发布两个文件后，列表按顺序含两个）；说明含“工作文件留在电脑上”。
- `computer_files` 写入经真实的 guest 回到宿主工具，结果带 `location`（`internal/computer/guest/write_location_test.go` 是 guest 侧的同一断言）。

## 提示词预算

系统提示词没有改，`prompt_budget_test.go` 的上限不变（全绿）。变长的是不在系统提示词里的三处：`say` 工具说明 +145 字符、完成复核文字 +629 字符（只在武装的 run 里随那一次退回出现一次）、`publish_file` / `computer_files` 的说明各一句。

## 约束（owner）

不硬编码、不为测试定制、不写任务专属的工具或文字；提示词只写原则（没有示例、没有“不是……而是”、没有关键词表，测试守着）；照 Anthropic 做；产品逻辑里不做关键词匹配；交互回复不变慢（没有新增模型调用）。

## 参考

- Anthropic，《Writing effective tools for AI agents》：工具返回的是对模型有意义、足以决定下一步的信息（高信号字段，而不是内部标识），并在说明里写清做什么、何时用。本决定把“文件放在哪”“发布了什么”“排的是哪个时区”作为事实放进工具结果，而不是靠提示词让模型去猜。
- Anthropic，《Building effective agents》：每一步从环境取得真实结果作为依据，agent 的汇报以这些结果为准。本决定把这一条落到最终回复的逐句核对上。
- 相关内部决定：[D01](0001-persona-generator-no-examples.md)（提示词只写原则）、[D09](0009-reliability-principles.md)（“已核实”要真查过）、[D40](0040-lookup-at-the-point-of-decision.md)（在决策点放原则）、[D43](0043-answer-gate.md)（定时回答的评分闸，聊天回复不评）、[D41](0041-builtin-deliverable-skills.md)（技能里的“回复对文件成立”）。

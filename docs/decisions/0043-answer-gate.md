# 0043 回答闸：草稿先过评分员，不合格才退回，补救办法由 Bot 自己想

> 编号 D43，索引见 [README](README.md)。

## 决定

Bot 的 `say(answer)` 草稿在人看到之前，先交给一个独立的评分员按一份评分标准打分；有不合格项，就把不合格项的清单私下交还给 Bot 重写，由 Bot 自己决定怎么改进（查记忆、搜历史、上网、读文件、重新想，都行）。这是 Anthropic 的 evaluator–optimizer 工作流（《Building effective agents》）和 Managed Agents 的 outcomes 评分员的做法。

1. **评分标准**是一份嵌进二进制的 markdown（`internal/app/answer_rubric.md`），四条通用的、可逐条评分的标准，只写原则、不点名任何补救办法：回答了所问（C1）、不需要追问（C2）、不过早放弃或把活推回给人（C3）、形式和语气合适（C4）。每条独立评分。
2. **评分员在自己的上下文里**，看不到 Bot 的推理和做过什么（没有工具记录，按 owner 的要求）。它只看：这个人的请求、这个人能看到的最近对话（最近 12 条，每条最多 800 字）、被评的回复和回复所附文件的名字。它返回逐条结果 `{"id","result":"met"|"gap","note"}`；总判定由 Go 从枚举推出（有任何 `gap` 就退回），Go 里没有任何文字匹配。解析是严格的：每条标准恰好一次、取值在枚举内，否则算评分失败。
3. **循环**：不合格项（标题加一行说明，不带标准编号）经现有的“瞬时拒绝”机制私下送回 Bot（`answer_revise`），草稿被替换、不展示。设置 `answer_gate`（设置 › 自动行为 › 检查，“定时和后台任务交付前先复核”）是最多评分次数：默认 2，范围 0–5，0 表示关闭。到了上限，最新的一稿直接发出（第 N+1 稿不再评分）。评分员失败、超时（20 秒）、答非所问，都直接发出草稿。
4. **展示**：评分可能发生时（只有定时任务），`say(answer)` 的正文不流式输出，通过后整段交付。附带 wake 名单的回答不评分（那是交接说明）。聊天回复的流式输出走和 `main` 完全相同的代码路径。
5. **评分员的模型**用后台模型设置（`background_model`）：Anthropic 对话用 Haiku；只连了 Codex 的工作区用最小的 Codex 模型（`codex-gpt-5.6-luna`）；没有可用的评分模型时这一轮不启用，回答照旧流式输出。不新增模型设置。
6. **范围（owner 定：只评没有人在等的活）。** 评分的是定时任务的回答，包括群里的定时任务（`Kind == "schedule"`，或通过 `scheduleTask` 识别出的定时运行）。按代码里的运行种类（`collaboration.go`、`group_mention.go`、`app.go`）逐个看：
   - 评分：`schedule`。它不是任何人的消息触发的，结果是之后才读的报告。
   - 不评分：`""`（私聊里人发的消息）、`group_chat`（群里人发的消息）、`group_mention`（Bot 在群里点名另一个 Bot，属于人发起的那一轮）、`team`、`message`、`group_task`、`group_followup`（人发起的任务拆出去的委派和回传，人在等最终结果）。代码里没有别的“没人在等”的运行种类（没有触发器或自动化运行种类；主动跟进走的是定时任务/另一条流水线，不是 `Run` 种类）。
   - 同样不评分：隐藏或内部会话、分诊、非结构化输出、纯文字结尾、定时任务里的“回执修复”那一次尝试（只允许一次尝试，被退回会让回执失败）、带 wake 名单的回答。
   - 理由：第一版把所有回答都评了，聊天回复的可见延迟大约翻倍（见实测）；评分员本来就是 Anthropic 给“有目标的任务”用的，不是给聊天用的。聊天里“早先说过的事”由记忆和摘要解决（[D44](0044-recall-context-memory-and-search.md)）。
7. 工具工作后的“完成复核”（D 里的 `completion_review`）原样保留，先于评分员触发一次。

## 参考

- [Define outcomes（Managed Agents）](https://platform.claude.com/docs/en/managed-agents/define-outcomes)：评分标准是 markdown，逐条独立评分；评分员用独立的上下文窗口，不受主 agent 实现选择影响；返回哪些标准通过或失败的说明，交还给 agent 下一轮；`max_iterations` 默认 3、最大 20；结果 `satisfied` / `needs_revision` / `max_iterations_reached` / `failed`。
- cookbook《managed-agents-cma-verify-with-outcome-grader》：评分员“看不到写作者的推理”，只收到评分标准和产物；要求每条标准都有判定；标准要具体可评，“泛泛的标准会让评分员浮皮潦草”；循环到满足或到上限。

## 与 Anthropic 做法的偏离（逐条）

1. **评分标准固定且内置**，不是每个会话由调用方给。
2. **评分员多看了一段对话。** Anthropic 的评分员只看标准加产物；我们的产物是对话里的一句回复，没有上下文没法评，所以给了最近 12 条可见消息。
3. **评分员的模型是我们的选择**：Anthropic 没公布评分用哪个模型。我们用后台轻量模型（Haiku / luna）求快；理由和延迟数字见下。
4. **次数设置**：默认 2、范围 0–5（Anthropic 默认 3、最大 20），0 表示关闭（Anthropic 的 outcome 本来就是可选的）。到上限后最新一稿直接发出，没有 Anthropic 那一轮“确认回合”。
5. **逐条结果是结构化 JSON**（met/gap 加一行），总判定由 Go 推出；Anthropic 返回的是一段说明文字。
6. **评分员没有工具**，不能像 Anthropic 的评分员那样打开文件或网址去核对。因此**去掉了“事实有依据”这一条标准**：第一版有这一条，评分员看不到回复是怎么来的，把所有从历史或网页里查来的具体事实都标成“没有依据”，逼着 Bot 一遍遍重搜。能评分的只剩从读者角度看得出来的东西。评分员的提示里也写明它只看到对话的一部分、不核实事实。
7. **回答先压住、通过后整段显示**，Anthropic 的 outcome 是会话级别的，没有“展示前”这个概念。
8. 评分员的失败/超时发出草稿，是我们的取舍。

## 被去掉的做法和原因

- **自我标签 `resolution`（resolved / gap）加“没查过就退回”的规则**：把“去查”写死成唯一补救，而且只有模型自己认为有缺口才触发；实测 Sonnet 把泛泛的建议标成 `resolved`，闸不动。
- **并行输入检查（路由）**：同样把补救写死为“去查”，而且在快模型上赢不了简短回答（Codex terra 的一次实测：答案在 +1.90 s，检查在 +1.93 s 才回来）。
- 共同的错：把一个失败模式的补救办法写进了代码。现在代码只管“草稿合不合格”，怎么补救是 Bot 的事。

## 实测（以下是评分员对所有回答都开着的版本，也就是 owner 否决的范围；聊天延迟翻倍的数字来自这里。本机，Sonnet 5.5 做 Bot，Sonnet 5.5 评分员，Haiku 做回复评分员，全新 Bot，每项 3 轮）

“前”是 `main` 的二进制；“后”是本分支。种子历史直接写进数据库，把事实挤出 32000 字符的窗口。**答案可见时间**是从人的消息发出到 Bot 的第一条可见回复入库（完整答案一次入库；“前”的版本其实更早就开始流式出字，这个时间没有保存，所以“前”的感知延迟比表里低）。每格为 完成 / 答错或无据 / 触发退回的 run 数。

| 任务 | 前 完成 / 错 / 退回；答案可见 均值 · p90 | 后（最终评分标准）完成 / 错 / 退回；均值 · p90 |
|---|---|---|
| 回忆：猫粮（事实在窗口外） | 0 / 2 / 0；3.4 s · 3.6 s | 0 / 1 / 0；5.3 s · 6.0 s（第二版标准，n=3，未再测） |
| 回忆：报名链接 | 3 / 0 / 0；4.8 s · 5.5 s | 3 / 0 / 2；12.9 s · 16.8 s |
| 网上可查（美联储） | 3 / 0 / 0；4.8 s · 5.5 s | 3 / 0 / 0；8.6 s · 9.5 s |
| 问候（含评测器补的“go ahead”） | 1 / 1 / 0；4.1 s · 8.5 s | 0 / 0 / 3；3.7 s · 4.2 s |
| 直接问题 | 3 / 0 / 0；4.3 s · 8.4 s | 3 / 0 / 0；3.5 s · 3.9 s（第一版标准，n=3） |

- **延迟**：评分一次约 1.4–4 s（Haiku）；通过的回答每条多这一次；被退回的多一整轮 Bot 加一次评分，回忆和网页类约 +8–17 s。所有任务合并（最终标准：链接、网页、问候共 9 条）答案可见均值 8.4 s、p90 16.8 s，而“前”同样三个任务是 4.5 s 左右。
- **成本**：每次评分约 1600 输入、470 输出 token，按 Haiku 估价约 $0.004 一次。被退回的回答还要付 Bot 的下一轮。
- **第一版标准（含“事实有依据”）不能用**：网页和链接题几乎每条都被退回（均值 21–23 s），评分员把查来的事实当作没依据。这是上面第 6 条偏离的由来。
- **没解决的**：回忆（猫粮）题。窗口外的事实评分员看不到，Bot 给了泛泛的建议，评分员也认为是一个正常的回答，没有退回。评分员只能抓“看得出来的坏回答”（放弃、推回给人），抓不到“回答得很流畅但漏了这个人早先说过的事”。这是“评分员看不到过程、也看不到全部历史”的结果。
- **评分员过严的残留**：报名链接任务里，评分员仍把窗口外的真实细节当作编造（2/3 被退回），Bot 重搜后答案不变，白付了 8–10 s。
- **花费**：这一轮估价合计约 $13（“前”2.9、“后”4.6、两次调标准 3.4 和 2.2；估价按未命中缓存算，是上限），超出了 $8 的预算，原因是第一版标准的几乎全退回和两次重调。
- Codex terra 上的“前/后”由协调者另行测，不在这里。
- 缩小范围后的验证：一次本机端到端，定时任务的回答被评分并在有 gap 时被退回（见下方“范围验证”）；聊天回复不评分、流式输出由测试 `TestPersonTriggeredAnswerStreamsAndIsNeverGraded` 保证。

## 范围验证（本机，Sonnet 5.5，约 $0.42）

用评测任务 `remind_stretch_3min` 在本机服务上端到端跑了一遍：这一任务里有 2 个聊天回合（私聊）和 1 个定时回合。服务日志里只有一行 `[answer-grade]`，属于定时回合（Haiku 评分，iteration=0，gaps=0，3.07 s，通过后交付）；两个聊天回合没有评分调用。退回路径（有 gap）由单元测试覆盖，这次线上没有触发。
